## Подтверждённые находки

### 1. P1 — публичный rate limiter не ограничивает рост памяти

`src/face_moment/serving_control/display_client_auth.py:49-50,64-79` создаёт запись для каждого нового token digest до проверки, что IP уже исчерпал лимит. Истёкшие deque очищаются лишь при повторном обращении к тому же ключу; сами ключи никогда не удаляются. `src/face_moment/entrypoints/realtime.py:270-283` применяет этот лимитер к публичному realtime маршруту. Аналогичный бессрочный словарь ключей есть у входа сотрудников (`src/face_moment/platform/auth/sessions.py:86-99`) и публичного phone flow (`src/face_moment/promo/qr_continuation.py:103-118`). Контрольная проба выше подтверждает, что IP‑лимит не сдерживает число новых token keys.

Влияние: поток неверных Bearer tokens способен постоянно увеличивать память долгоживущего процесса, в том числе когда запросы уже получают `429`. Минимальное направление: проверять исчерпание IP‑бюджета до создания token entry, удалять истёкшие пустые записи и ограничить число ключей; проверить рост при множестве неверных токенов. Фактическое потребление памяти production процесса не измерялось.

### 2. P1 — browser regression suite сейчас не даёт зелёного сигнала

Project runner объявлен в `package.json:5-8`. Его запуск дал 17 failures из 37 без общей ошибки запуска браузера или fixture. Как минимум девять сценариев `tests/client/test_browser_recovery.spec.mjs:211,223` и `tests/client/test_degraded_advertising.spec.mjs:280-286` ждут `#replay-last-promo`, которого текущий клиент не создаёт: replay управляется карточкой в `client/app.js:223-233`. `tests/client/test_promo_replay.spec.mjs:71` ждёт исчезновения Promo за 3 секунды, хотя текущий переход сначала делает трёхсекундный fade (`client/app.js:51-63`), а затем удаляет карточку (`client/promo-display.js:685-708`). Остальные падения затрагивают BlazeFace, SPA settings и скрытые staff controls; их общая причина этим аудитом не установлена.

Влияние: browser suite не может служить надёжным регрессионным gate, а реальные дефекты среди 17 падений трудно отделить от устаревших ожиданий. Минимальное направление: обновить подтверждённо устаревшие селекторы и временные ожидания по текущему контракту, затем отдельно разобрать оставшиеся failures и повторить suite. Успешные 80 клиентских unit tests этот пробел не закрывают.

### 3. P2 — публичный runtime допускает известные development secrets

`compose.yaml:10,13,26,68-70,88-89` подставляет известные значения для PostgreSQL, MinIO и QR key при неполной конфигурации. `src/face_moment/infrastructure/settings.py:9,163-165` независимо принимает известный QR key по умолчанию. QR ticket выводится через HMAC с этим ключом (`src/face_moment/promo/session.py:362-375`); `compose.yaml` является и release topology согласно `.memory-bank/guides/local-development.md:19`.

Влияние: публикация edge с неполным env не отклоняется заранее и работает с предсказуемыми секретами. Минимальное направление: отделить явные локальные значения от release конфигурации и требовать непустые, нештатные секреты до открытия runtime. Фактические значения на внешнем сервере не проверялись; вывод касается допустимого пути запуска, а не доказанной компрометации.

### 4. P2 — обработанный отказ Photo admission оставляет candidate в MinIO

`src/face_moment/inventory/photo_upload.py:123-135` сохраняет request-owned candidate до публикации Photo. `src/face_moment/inventory/admission.py:99-111` вызывает cleanup лишь при распознанном duplicate; иной `IntegrityError` или исключение откатывает транзакцию, но не удаляет объект. Добавленная в `ab8fe60` `admission_storage_guard` защищает параллельный ручной обход orphan keys (`src/face_moment/inventory/orphan_original_cleanup.py:35-81`), но не очищает candidate в этой ветке. Контракт `.memory-bank/domains/photo-admission.md:150-154` предусматривает очистку обработанного отказа; orphan при аварийном завершении процесса отдельно принят в строках 185–192.

Влияние: повторяемые ошибки БД/initial pending после upload накапливают приватные объекты без Photo ссылки, занимая MinIO; ручная уборка не устраняет источник. Минимальное направление: на обработанном non-duplicate отказе удалить только candidate этого запроса, не маскируя исходную ошибку; проверить rollback и cleanup вместе. Добавленная operator cleanup может удалить накопившиеся объекты при отдельном запуске, но не заменяет request cleanup.

### 5. P2 — удаление рекламы теряет возможность повторить MinIO cleanup

`src/face_moment/promo/advertising_http.py:159-173` удаляет media row и playlist reference, коммитит БД, затем удаляет бинарный объект. Если последний вызов падает, HTTP отвечает ошибкой после завершённого удаления БД; повторный DELETE попадает в `404` на строках 163–165. Размер одного разрешённого файла доходит почти до 2 GiB (`advertising_http.py:140-146`).

Влияние: сбой MinIO оставляет крупный приватный orphan без ключа в рабочем API и без штатного retry. Минимальное направление: сохранить row/key до успешного идемпотентного удаления объекта, затем завершить DB mutation так, чтобы повтор DELETE мог довести операцию до конца. Наличие таких объектов в текущем MinIO не проверялось.
