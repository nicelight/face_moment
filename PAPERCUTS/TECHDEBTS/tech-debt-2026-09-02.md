# Технический долг проекта — порядок закрытия

Проверен текущий код проекта, включая незакоммиченные результаты FT-008 и
FT-009. Шесть findings расположены не только по важности, но и по
зависимости друг от друга: сначала достоверность проверок, затем локальные
расхождения и только после них широкие изменения общей структуры. Закрытая в
`TASK-094-T3-FT-009-W1` проблема с чтением ORM-объекта после commit сюда не
включена.

## 1. Docker-проверка может запускать устаревший код

**Закрыт 2026-09-02.** Проверки и Python-роли теперь запускаются из текущего
working tree через `uv run --locked`; в ежедневном Docker-контуре остались
только PostgreSQL и MinIO. Полный Compose используется отдельно и всегда
пересобирает image перед packaged-runtime smoke.

До закрытия обычный `docker compose run` использовал установленный в image
пакет и не подтверждал его соответствие текущему рабочему tree. На момент
оценки source уже содержал исправление FT-009 из `TASK-094`, но стандартный
image импортировал старую сигнатуру emitter из `site-packages`. Этот же механизм
проявлялся в FT-004 (`TASK-068`, `TASK-069`, `TASK-074`) и FT-008 (`TASK-088`,
`TASK-089`), а сама сборка относится к FT-000 (`TASK-001`, `TASK-002`). Это
самый важный finding, потому что любой последующий тест или рефакторинг теряет
смысл, если проверяется другая версия программы. Изменение имеет среднюю
глубину и ограничено подтверждением актуальности image и устройством
кэширования в `Dockerfile:11-13`.

## 2. Realtime-адреса вручную перечислены и в приложении, и в Caddy

Realtime endpoints определены в FastAPI и отдельно повторены в matcher
`deploy/Caddyfile:16,38-45`. Базовый маршрут появился в FT-003 `TASK-045`, а
при добавлении child route в FT-007 `TASK-083` его уже забыли внести в Caddy,
поэтому рабочий endpoint оказался недоступен через пользовательский адрес.
Finding имеет среднюю важность и небольшую либо среднюю глубину в зависимости
от того, нужен ли проекту строгий список разрешённых путей. Он расположен рядом
с предыдущим, потому что оба затрагивают одну и ту же границу Caddy и её tests,
а разнесение этих изменений создаёт повторную работу.

## 3. Постоянный тест восстановления браузера ненадёжен

Browser-recovery test из FT-003 `TASK-054` не запускается в чистом окружении:
`tests/client/test_browser_recovery.spec.mjs:7-8` не может найти
`playwright/test`. Одновременно fixture сохраняет `sensor_id`, хотя
production-код в `client/sensor-config.js:14-40` ожидает `sensorId`, и после
перезапуска сравнивается только необработанное содержимое localStorage. Test
поэтому способен принять неработоспособную конфигурацию как восстановленную.
Важность средняя, глубина небольшая или средняя. После первых трёх findings он
завершает восстановление надёжной постоянной проверки backend, edge и browser
поведения перед изменениями бизнес-логики.

## 4. Состояние показа результата вычисляется в двух местах

**Закрыт 2026-09-02.** Эффективный переход `pending -> unconfirmed` теперь
вычисляет одна чистая функция рядом с `PromoAttempt`; её используют и display
outcome, и diagnostics timeline. Схема, хранимый статус и API не изменились.

До закрытия переход `pending` в `unconfirmed` после истечения времени был
независимо описан в `promo/display_outcome.py:213-221` и
`promo/client_timing.py:144-153`. Первое
правило появилось в FT-005 `TASK-077`, второе — в FT-007 `TASK-083`, а его
результат используют FT-007 `TASK-085` и FT-008 `TASK-088`/`TASK-089`. Эти
реализации уже расходились и показывали разные состояния одной попытки.
Finding имеет среднюю важность и небольшую глубину, поскольку затрагивает одно
общее вычисление без изменения схемы хранения. После стабилизации проверок это
самый компактный смысловой рефакторинг с уже подтверждённой историей ошибки.

## 5. Подключения к базе данных создаются заново для каждого HTTP-запроса

**Закрыт 2026-09-02.** Backend composition root теперь создаёт один
SQLAlchemy Engine на lifecycle приложения и передаёт HTTP-модулям factory
коротких Session; при shutdown Engine освобождается. Diagnostics writer
сохранил независимую Session и не затронул realtime.

До закрытия одинаковая работа с базой повторялась в `platform/auth/http.py:131-137`,
`inventory/http.py:214-220`, `serving_control/http.py:160-166`,
`diagnostics/http.py:259-265` и `promo/http.py:470-476`. Каждый запрос создавал
собственный SQLAlchemy Engine и сразу уничтожавал его, поэтому постоянный пул
соединений почти не использовался. Долг накоплен в FT-001 (`TASK-004`,
`TASK-015`), FT-004 (`TASK-068`), FT-005/FT-006 (`TASK-076`, `TASK-077`,
`TASK-081`) и FT-008 (`TASK-089`). Важность средне-высокая, глубина средняя.
Он затрагивает общую сборку backend и сразу пять HTTP-модулей, то есть имеет
широкий радиус изменения.

## 6. Переключение рабочей версии обработки неявно требует чистую DB Session

Команда FT-002 `TASK-040` открывает новую transaction в
`serving_control/ingest_target.py:124-132`. Если на той же Session уже было
обычное чтение или проверка пользователя, SQLAlchemy считает transaction
начатой и команда завершается `InvalidRequestError`. Пользовательского API для
переключения пока нет, а tests всегда используют новую Session, поэтому
проблема остаётся скрытой. Сейчас её важность низкая, глубина небольшая;
зависимый guard из `TASK-039` к причине не относится. Последнее место отражает
не меньшую корректность finding, а отсутствие вызывающего API: практический
риск возникнет только при его появлении.

Оценка DB lifecycle не опирается на production load test, а browser recovery
не повторялся на pilot host. Эти ограничения не меняют порядок: edge/browser
findings определяют качество соответствующих доказательств, а последний пока
не имеет доступного пользователю пути выполнения.
