# Capture preparation can leave the search animation active

Observed: the operator reported a two-face capture remaining on the detection
caption for five minutes. The inspected backend has no Attempt newer than
`00ee73b7-ea3a-46f6-92ab-573989988fd6`, which predates the reported capture.

In `client/app.js`, the reference-series handler awaits detector initialization,
`setThreshold` and `detectReferenceSeries` without a deadline. If one never
settles, neither submission nor the failure cleanup executes. Early stale
returns also leave cleanup dependent on another lifecycle handler.
The exact stalled call is not established without the affected browser's
console/state. Configuration loading separately has a five-second deadline.
The number of faces is not yet proved causal. No hang fix was authorized or
applied; the requested visible client Attempt ID was implemented separately.

## Confirmed cause and authorized resolution

The supplied browser state retained `triggerState=searching`,
`attemptState=advertising` and the initial series-ready message. A deterministic
execution of the app handler with the real JPEG quality controller reproduced
the cause: successful display finished by request UUID, while the JPEG snapshot
was keyed by capture ID. The old snapshot survived; the next capture returned
at the stale-identity guard after loading configuration and never called the
detector. Two faces were not causal in this reproduction.

After explicit operator approval, app wiring now retains the active
request/capture binding and resolves completion to the capture ID. Both finish
listeners ignore unrelated completion. Regression covers successful display,
render failure, pre-request failure, stale completion and next-search submission.
The earlier no-deadline observation is not the established cause of this hang;
no timeout or detector changes were made.
