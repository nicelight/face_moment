# FT-012 — Photo Inventory Operations

**Epic:** [EP-001 — Fresh Searchable Inventory](../epics/EP-001.md)

## Outcome

Authorized photographers and staff can find commercial Photos by venue, date
and capture-time range, hide or restore them within their role, observe recent
per-СПА processing activity, and permanently purge all soft-deleted media
through one controlled project-wide operation.

## Accepted Feature Boundary

On 2026-07-24, the operator explicitly accepted FT-012 as one planning and
completion boundary for the current pilot, covering both role-scoped
deletion/restore/global purge and recent per-СПА 1/5/60-minute counters. The
read-only counters remain part of FT-012 even though they are independently
testable. Splitting or renumbering this boundary requires a new explicit
operator decision.

## Requirements

- `REQ-INV-001`, `REQ-INV-002`, `REQ-INV-003`, `REQ-INV-004`.
- Cross-cutting: `REQ-ARCH-001`.
- Registry: [.memory-bank/requirements.md](../requirements.md).

## Use Cases

- A photographer selects one СПА, authoritative `visit_date` and capture-time
  range, then soft-deletes or restores only Photos uploaded by that
  photographer.
- An operator or developer soft-deletes or restores any Photo in an accessible
  СПА using the same selection scope.
- Staff view separate per-СПА `new`, `unprocessed`, `processed` and `failed`
  counters for the last 1, 5 and 60 minutes.
- An authorized operator/developer restores every soft-deleted Photo across the
  project except members of a confirmed non-terminal hard-purge snapshot.
- An authorized operator/developer confirms permanent deletion of every
  currently soft-deleted Photo and observes worker wait/progress until
  completion.

## Acceptance Criteria

### FT-012-AC-001 — Role-scoped inventory selection

- REQ: REQ-INV-001, REQ-INV-002
- Observable criterion: Selection uses one СПА, authoritative `visit_date` and
  effective `captured_at`, derived from reliable EXIF in the СПА timezone,
  otherwise file upload-start time, otherwise 01:00 on `visit_date`.
  Photographers can act only on their own uploads; operator/developer scope is
  limited to accessible СПА, and project-wide actions remain admin-only.
- Verification: Exercise every timestamp fallback and role/scope combination
  through list, soft-delete, restore and global-action authorization checks.

### FT-012-AC-002 — Soft-delete and restore continuity

- REQ: REQ-INV-002
- Observable criterion: Soft delete preserves Photo/media/faces/pipeline state
  but immediately excludes the Photo from new search/result formation and all
  recent counters while an already issued session may keep using existing
  media; restore reactivates the preserved state/timestamps without upload or
  reprocessing.
- Verification: Compare search, statistics, stored data and issued-session
  reads before delete, while deleted and after restore.

### FT-012-AC-003 — Restore-all snapshot exclusion

- REQ: REQ-INV-003
- Observable criterion: `restore all soft deleted` restores every currently
  soft-deleted Photo across the project except members of a confirmed non-
  terminal hard-purge snapshot, whose individual and global restore attempts
  are rejected until purge completion.
- Verification: Confirm a purge snapshot, add another soft delete, run
  restore/restore-all before and after completion and compare active states.

### FT-012-AC-004 — Confirmed fixed-snapshot purge progress

- REQ: REQ-INV-003
- Observable criterion: `hard delete ALL softed media` requires confirmation
  that fixes the project-wide snapshot. If the shared worker is occupied, purge
  waits without preemption and shows
  `Начну удаление, как только закончится процесс {human-readable process name}`;
  while running, completed/total progress replaces the destructive interface.
- Verification: Start purge with idle and occupied workers and inspect
  confirmation target set, waiting copy, operation order and progress UI.

### FT-012-AC-005 — Resumable ownership-safe hard purge

- REQ: REQ-INV-003, REQ-ARCH-001
- Observable criterion: The one global run resumes the same fixed snapshot after
  backend/worker restart, never interrupts an upload already in progress and
  removes snapshot Photo/original/preview/thumbnail/face/pipeline data while
  retaining Promo sessions/results, core Attempts and diagnostic evidence.
  Existing clients skip absent media without session invalidation or issued-`N`
  recalculation.
- Verification: Interrupt purge after partial progress with concurrent upload,
  resume to completion and inspect every owned/retained record plus existing
  client reads.

### FT-012-AC-006 — Exact recent per-СПА counters

- REQ: REQ-INV-004
- Observable criterion: For each СПА, five-second polling returns separate 1-,
  5- and 60-minute values: `new` for active unique Photos accepted in-window;
  `unprocessed` for those accepted in-window and currently
  `pending|processing`; `processed` for active Photos transitioned in-window to
  `ready|no_faces`; and `failed` for active Photos transitioned in-window to
  `failed`. Soft-deleted Photos are absent and restored Photos use preserved
  timestamps.
- Verification: Evaluate boundary timestamps, state transitions, soft delete
  and restore against independent SQL/oracle calculations and observe polling
  cadence.

### FT-012-AC-007 — KISS inventory operation shape

- REQ: REQ-INV-003, REQ-INV-004, REQ-ARCH-001
- Observable criterion: Inventory operations reuse the shared worker and
  durable Photo data without per-photo `purge_pending`, a purge jobs table,
  another worker, WebSocket/SSE statistics or silent addition of Photos
  soft-deleted after confirmation to the running purge snapshot.
- Verification: Inspect schema/runtime topology and confirm late soft-deleted
  Photos remain eligible only for a later purge while statistics use polling.

## Edge and Failure Behavior

- Missing or unreliable EXIF time does not create a separate manual-resolution
  path; the deterministic upload-start/01:00 fallback keeps selection usable.
  Covered by `FT-012-AC-001`.
- Photos soft-deleted after a purge snapshot is confirmed are not silently
  added to the running snapshot and remain available for a later purge. Covered
  by `FT-012-AC-003` and `FT-012-AC-007`.

## Cross-feature Boundaries

- [FT-001](FT-001.md) supplies Photo uploader identity, authoritative
  `visit_date`, upload-start timing and `accepted_at`; FT-012 owns the inventory
  action scope and effective capture-time fallback.
- [FT-002](FT-002.md) owns normal Photo processing-state transitions; FT-012
  only uses those preserved states for visibility, restore and counters.
- [FT-004](FT-004.md) uses only active inventory for new search.
  [FT-006](FT-006.md) may continue an already issued session across soft delete
  and skips unavailable media after hard purge.
- [FT-007](FT-007.md) continues to own core Attempts and diagnostic evidence;
  FT-012 hard purge explicitly retains them.
