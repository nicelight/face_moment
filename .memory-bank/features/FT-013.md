# FT-013 — Публичный поиск и персональная галерея

**Epic:** [EP-004](../epics/EP-004.md): публичный поиск и выбранные originals.

## Outcome

Посетитель без регистрации снимает селфи, выбирает площадки после съёмки,
находит свои фото и просматривает разрешённую ленту; при пустом поиске получает
понятный повтор с ограниченной паузой в этом браузере.

## Requirements

`REQ-PUB-001`, `REQ-PUB-002`, `REQ-PUB-003`, `REQ-PUB-006`, `REQ-PUB-007`, `REQ-PUB-008`, `REQ-PUB-009`.
Registry: [requirements](../requirements.md).

## Acceptance Criteria

### FT-013-AC-001 — Camera and retained local selfies

- REQ: REQ-PUB-001
- Observable criterion: Каждый снятый кадр сохраняется в IndexedDB как JPEG Blob сразу после съёмки; пересъёмка, отказ А/Б и неудачный или успешный поиск не удаляют историю. Начальные long edge<=960/quality .85 без upscale и лицо >=30% проверены на representative image fixtures без гарантии recall; native paired comparison принадлежит AC-007. При quota/недоступности пользователь видит предупреждение и продолжает текущий поиск без сохранения нового, прежние снимки не удаляются. История не отправляется автоматически; галерея/аватарка не являются input.
- Verification: Browser flow + decoded image/storage fixtures, including quota, no-upscale, retake, A/B denial and failed/successful search preserving captured history.

### FT-013-AC-002 — Explicit scoped search

- REQ: REQ-PUB-002
- Observable criterion: Server rejects empty/>3 selection; ищет только доступные совместимые undeleted даты выбранных площадок без Promo date narrowing и не раскрывает другие.
- Verification: Server scope fixtures including adversarial cross-venue photos and different dates.

### FT-013-AC-003 — Visible progress and result

- REQ: REQ-PUB-002
- Observable criterion: До явного «Найти меня» после выбора 1–3 площадок selfie не уходит на сервер. Browser показывает предупреждение А/Б перед «Это я»/reset и позволяет пересъёмку, применяя server outcome. Пользователь видит нескучную анимацию/progress и результат: число личных фото, имена площадок, даты. Имитированный progress не выдаётся за измеренный процент без серверных измерений. No-match/неудачный запрос не представляется успешным результатом; никакой signup не требуется.
- Verification: Browser journey, success/no-match/request-failure fixtures; human UX review checks visible engaged progress and clear state without false completed search; without server measurement, assert no simulation presented as measured percentage.

### FT-013-AC-004 — One-person A/B and invisible profile

- REQ: REQ-PUB-001
- Observable criterion: Существующий серверный скрытый профиль по protected cookie хранит фиксированные А/Б: любой match допускает; первое отличие заполняет Б; третье отличается -> «Это я»/«Переснять» без поиска; один подтверждённый reset заменяет оба новым А и вновь допускает Б; после reset mismatches отклоняются с принятой фразой, пересъёмка разрешена. Нет/несколько лиц/плохое качество не расходуют образцы/reset. Developer настраивает порог А/Б независимо от порога поиска профессиональных фото, без автоматического изменения последнего. Поиск использует только текущий selfie. Сохранённый профиль persists, last visit updates; cookie loss не восстанавливает историю. Отложенное сохранение нового профиля при первом `no_matches` проверяется AC-013.
- Verification: State-transition fixtures covering every accepted branch and replay/repeated access, plus persisted cookie/last-visit application-boundary check; assert warning precedes reset, authorized Developer threshold change affects A/B matching while professional-photo search threshold remains unchanged.

### FT-013-AC-005 — Ordered venue feed and free common photos

- REQ: REQ-PUB-003
- Observable criterion: Лента: venue heading -> personal watermarked reduced previews -> common -> next. no_faces только за даты личных совпадений и бесплатно везде. Watermark frontend removable, Promo/QR unchanged. Gallery использует защищённые уменьшенные preview с размерами/доступом по AC-009. Venue with no personal match grants no arbitrary-date common photos.
- Verification: Gallery fixtures for paid/free venues, dates, no_faces including people, browser watermark rendering; baseline Promo/QR scope check.

### FT-013-AC-006 — Protected public discovery

- REQ: REQ-PUB-008
- Observable criterion: HTTPS/profile/IP configured rate limit enforced; IP не identity. Requests over configured limit denied without photo search; stores/originals remain private and reduced previews не раскрывают originals. No liveness/fingerprinting/advanced bypass defense required.
- Verification: Public route/topology/access fixtures and configured-rate enforcement; no numeric rate target invented.

### FT-013-AC-007 — Native selected-venue search

- REQ: REQ-PUB-001, REQ-PUB-002
- Observable criterion: Processing готовит текущее selfie: ровно одно лицо, native quality gate immutable snapshot, compatible embedding; exact search возвращает только active ready Photos выбранных площадок по всем датам с per-venue threshold, без Promo narrowing/pHash eligibility.
- Verification: Native adapter и PostgreSQL scope fixtures, включая invalid face/quality, revision, несколько дат и чужую площадку; Promo search regression. Representative original → browser JPEG 960 px/q0.85 пары сравнивают реальные native face count/gate/embedding/matches при одинаковых revision/settings/corpus; фиксируют различия без новой accuracy guarantee.

### FT-013-AC-008 — Profile-owned current result

- REQ: REQ-PUB-002, REQ-PUB-003, REQ-PUB-008
- Observable criterion: Успешный public поиск сохраняет разрешённые personal/common IDs и metadata как текущий result своего профиля; cookie защищена, last visit обновляется явным действием. Busy/deadline/no_matches/denial не публикуют успешную галерею; чужой result недоступен. Personal.is_free получает сохранённый serving_control venue flag (existing venues default false); common всегда free.
- Verification: API/DB integration, повторное чтение result, cookie/last visit, competing Promo slot и failure outcomes без публикации; owner repository read/write paid/free flag, migration default false и result projection. Staff administration остаётся FT-014.

### FT-013-AC-009 — Private reduced preview bytes

- REQ: REQ-PUB-003, REQ-PUB-008
- Observable criterion: Только свой current result и active Photo позволяют получить уменьшенный JPEG шириной 640 px (>=320), включая historical no_faces; original bytes/key/URL не раскрываются. Недоступное/чужое фото даёт 404; IO/render ограничен одним backend executor, busy даёт 429.
- Verification: HTTP/media fixtures с decoded dimensions, private originals, historical no_faces и busy/missing/deleted/foreign result; Promo/QR bytes не изменяются.

### FT-013-AC-010 — White capture flash

- REQ: REQ-PUB-001
- Observable criterion: При нажатии «Жмак меня» для съёмки весь viewport вне существующего круга становится белым на 50–100 ms; круг остаётся видимым. Это не меняет сохранение кадра, параметры камеры или поиск.
- Verification: Browser capture на representative desktop/mobile viewport с проверкой белой области, сохранённого круга и длительности 50–100 ms.

### FT-013-AC-011 — Venues only after capture

- REQ: REQ-PUB-002
- Observable criterion: До готового текущего снимка выбор площадок скрыт и недоступен; после съёмки доступен выбор 1–3 площадок. Никакое selfie не отправляется до явного «Найти меня»; поиск остаётся по всем доступным датам выбранных площадок.
- Verification: Browser state/network journey до и после capture, server scope fixtures для 0/>3 площадок, выбранных площадок и нескольких доступных дат.

### FT-013-AC-012 — Exact empty result and retry action

- REQ: REQ-PUB-002, REQ-PUB-009
- Observable criterion: Завершённый `no_matches`, пока пауза AC-014 не наступила, показывает отдельный экран с [точным текстом из PRD](../prd.md#2026-10-07--capture-flash-post-capture-selection-and-empty-search-retry) и кнопкой «Попробовать еще», возвращающей к повторному поиску. Подсказка о трёх месяцах не ограничивает поиск всеми доступными датами.
- Verification: Browser fixture завершённого `no_matches` без активной паузы проверяет отдельный экран, точную строку/пробелы и действие повтора; search scope по всем доступным датам остаётся за AC-002/011.

### FT-013-AC-013 — No persistent profile for first unmatched visitor

- REQ: REQ-PUB-001, REQ-PUB-008
- Observable criterion: Первый `no_matches` нового посетителя не оставляет durable hidden profile, A/B samples или новой profile auth cookie; профиль сохраняется только после найденных фото. Поздний пустой поиск существующего профиля не удаляет его, А/Б или покупки. Browser-cookie cooldown AC-014 не является profile auth cookie.
- Verification: Server database/cookie integration на новый пустой поиск, первый успешный поиск, поздний пустой поиск существующего профиля и сохранность существующих заказов/покупок.

### FT-013-AC-014 — Browser-cookie retry limit and cooldown

- REQ: REQ-PUB-001, REQ-PUB-006, REQ-PUB-007, REQ-PUB-009
- Observable criterion: Браузер считает подряд завершённые `no_matches` независимо от reload и смены площадок. До пятого исхода повтор доступен через экран AC-012. Пятая подряд завершённая неудача сразу показывает [точный текст паузы из PRD](../prd.md#2026-10-07--capture-flash-post-capture-selection-and-empty-search-retry) и блокирует новый поиск до истечения 30 минут от этой неудачи. Счётчик и deadline хранятся только в browser cookie; после expiry счётчик очищается. Успешный поиск очищает счётчик; camera/network/server errors, `busy` и непригодное selfie не считаются. Очистка cookie или другой браузер могут обойти паузу; серверной истории cooldown нет.
- Verification: Browser fixtures на последовательность 1–5 completed `no_matches`, четыре доступных повтора, точную строку/пробелы пятого исхода, reload, смену площадок, блокировку POST во время cooldown, expiry от пятой неудачи +30 min, success reset и нерасходующие outcomes; cookie/network inspection подтверждает только browser-cookie состояние без новых server cooldown records.

#### Preparing-order continuity

- Observable criterion: Пауза запрещает только новый поиск. Уже созданный paid order в состоянии `preparing` остаётся доступен для owner status refresh и продолжения оплаты после готовности ZIP, даже если новый поиск очистил выбор и завершился `no_matches`. До redirect refresh проверяет тот же order и открывает оплату только после `ready`; после redirect refresh проверяет только server status. Новый непустой выбор сохраняет обычный `start()`; после reload до redirect восстановления заказа не обещано.
- Verification: HTTPS browser journey создаёт paid `preparing` order, затем выполняет новый поиск и пять реальных `no_matches`; при паузе доступны панель и refresh, owner GET использует тот же order ID, `POST /orders` за путь ровно один. После `ready` оплата продолжает этот заказ без второго order POST; pending после redirect не открывает paid link до server-confirmed success. Отдельно проверяются прежний post-redirect refresh и новый непустой выбор. Cookie/count proof остаётся за TASK-150, платёжный post-redirect contract — FT-016-AC-005.
