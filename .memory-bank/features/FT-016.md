# FT-016 — Покупка и скачивание выбранных платных фотографий

**Epic:** [EP-004](../epics/EP-004.md): публичный поиск и выбранные originals.

## Outcome

Посетитель оплачивает один общий выбор нескольких площадок и получает выбранные originals; бесплатные фото в выборе остаются бесплатными.

## Requirements

`REQ-PUB-001`, `REQ-PUB-004`, `REQ-PUB-005`, `REQ-PUB-006`, `REQ-PUB-007`, `REQ-PUB-008`. Registry: [requirements](../requirements.md).

## Acceptance Criteria

### FT-016-AC-001 — One frozen mixed order and email

- REQ: REQ-PUB-001, REQ-PUB-004, REQ-PUB-005, REQ-PUB-006
- Observable criterion: Один заказ включает all selected across venues, freezes authoritative composition/RUB quote/free access. n excludes free/common. Paid flow asks email, stores profile email for receipt and updates last visit; no signup. Manual refund handling, no automatic refund platform. Если после quote, но до POST нового заказа площадка переключилась из бесплатного режима в платный, browser показывает «Условия изменились, выберите фотографии повторно» и позволяет обычный новый выбор; автоматическое продолжение оплаты для прежнего выбора не требуется. Созданный заказ сохраняет свою frozen сумму и free flags.
- Verification: Order/quote/browser email fixtures, mixed-venue selection, changed settings preserving old order and profile observation; served free-to-paid transition between quote and POST shows the message and permits fresh selection without claiming an order or payment form.

### FT-016-AC-002 — Ready archive before provider form

- REQ: REQ-PUB-006, REQ-PUB-007
- Observable criterion: Server payment initiation uses only ready, available, unexpired paid ZIP. Requested/preparing/failed archive never starts provider/payment; archive failure keeps existing admin-mail failure behavior. Frozen amount/email/method drive YooKassa receipt and form.
- Verification: Actual payment route/provider-adapter fixtures with pending/ready/failure; assert zero provider initiation before ready and frozen receipt data. Configured YooKassa TEST join covers bank_card redirect and frozen receipt payload. СБП проверяется через реальный application route и изолированный fake HTTP provider: `payment_method_data.type=sbp`, frozen receipt, idempotence и ошибки; browser continuation покрывает AC-005. До включения СБП в production обязателен отдельный внешний redirect/receipt proof в настоящем магазине с явным разрешением оператора; до него внешний SBP join не считается пройденным.

### FT-016-AC-003 — Server payment confirmation gates originals

- REQ: REQ-PUB-006, REQ-PUB-008
- Observable criterion: Only YooKassa; return browser не grants paid originals. Server confirms paid order before bearer access. Repeated payment confirmations do not duplicate purchases; incomplete/unsuccessful payment leaves paid access closed. Refunds manual; frozen receipt acceptance belongs AC-002.
- Verification: Provider-adapter contract/integration fixtures for server-confirmed, unconfirmed/cancelled and duplicate events, browser-return bypass denial.

### FT-016-AC-004 — Paid archive TTL and unavailable media

- REQ: REQ-PUB-007, REQ-PUB-008
- Observable criterion: Confirmed selection gets only selected originals; bearer works across device independent cookie, expires archive ready+3 days (not payment+3days). Private original bypass denied. Deletion may make media unavailable; clear error/manual support/refund, no archive shielding or restoration promise.
- Verification: Time-boundary/member/access fixtures incl delayed payment, cookie loss, missing original/archive and post-expiry access.

### FT-016-AC-005 — Paid browser preparation and continuation

- REQ: REQ-PUB-006, REQ-PUB-007
- Observable criterion: «Скачать» -> email and card/QR method -> archive preparation -> provider form only after ready. Preparing shows retry in 30 seconds; failure shows safe error without provider navigation. После pending возврата от provider retry проверяет фактическое число выбранных фото: при пустом выборе обновляет статус сохранённого заказа, при непустом продолжает обычный start() для выбора. Return/status refresh grants download only after server confirmation; unavailable/expired delivery shows manual support/refund guidance.
- Verification: Served browser with actual isolated backend and fake provider/mail covers preparation, failure, card/SBP redirects, unconfirmed return, confirmed link and unavailable delivery; after return and new search, retry with empty selection sends owner status GET for saved order, while nonempty selection follows ordinary start().

## Clarifications

- 2026-10-06: Оператор принял KISS repair для двух browser-сбоев финальной проверки TASK-139. При смене площадки free-to-paid после quote до POST показать «Условия изменились, выберите фотографии повторно» и дать обычный новый выбор без автоматического продолжения прежней попытки. После pending возврата от provider и нового поиска retry проверяет фактическое число выбранных фото: пустой выбор обновляет сохранённый заказ через существующий `controller.refresh()`, непустой сохраняет `start()`. Созданный заказ по-прежнему фиксирует сумму/free flags; доступ к платному архиву зависит только от серверного подтверждения оплаты. Новых server/schema/provider контрактов, состояний, history или polling platform нет. Исторический TASK-139 FAIL остаётся неизменным; требуются successor planning и новая независимая проверка.

- 2026-10-05: Оператор принял разделение proof для card/СБП: card и frozen receipt проверяются внешним TEST join; СБП — через реальный application route и изолированный fake HTTP provider. Реальный магазин нужен для внешнего СБП redirect/receipt proof перед production enablement, без production calls сейчас. Оба способа остаются в продукте. Merchant inputs: ИП, УСН «доходы», без НДС, описание «Оказание цифровых услуг»; реализация использует эти значения и проверяет наблюдаемые ответы API. Credentials хранятся в игнорируемом `.env.yookassa.local`. Фактический режим регистрации чеков и выпуск чека не входят в заявленное доказательство внешнего TEST card join.
