# FT-003 — Sensor-triggered Capture

**Epic:** [EP-002 — Automatic Promo and QR Continuation](../epics/EP-002.md)

## Outcome

A participant's passage starts one fresh, bounded reference capture without
participant input. The central-origin Chromium client submits the first at most
20 chronological BlazeFace occurrences through one structurally bounded
multipart request while overlap, stale work and central-runtime outages cannot
replace the safe local-advertising state.

## Requirements

- `REQ-CAP-001`, `REQ-CAP-002`, `REQ-UX-004`, `REQ-REL-001`,
  `REQ-PERF-001`.
- Cross-cutting: `REQ-SEC-001`, `REQ-SEC-002`, `REQ-ARCH-001`.
- Registry: [.memory-bank/requirements.md](../requirements.md).

## Use Cases

- Maintain a short camera ring buffer while local advertising is visible.
- In the client configuration UI, inspect the currently available USB UVC and
  other browser-visible video inputs, preview them and select the camera used
  for reference capture.
- Receive passage events from one autonomous ESP32 sensor on the same local
  network as the client through one authenticated 10-second HTTP long-poll at a
  time to its fixed mDNS `.local` name.
- Start the same capture path from an explicit test-trigger control in the
  client configuration UI without requiring the physical sensor.
- Use one sensor event to form the configured pre/post-trigger reference series.
- Traverse the ready series chronologically with BlazeFace Full-range, preserve
  its occurrence order within a frame and stop as soon as occurrence 20 is
  found.
- Crop and encode the first at most 20 occurrences and submit their manifest
  and JPEG parts in one synchronous multipart request.
- Select one of the six accepted JPEG quality values on the
  configuration/debug page for application from the next Attempt.
- Submit attempt metadata without crops when the detector returns no proposals.
- Prevent another trigger from starting capture while capture/search/cooldown
  owns the active attempt.
- Recover to local advertising after camera, network, service or browser failure.

## Acceptance Criteria

- Capture starts automatically from the passage sensor without a participant
  button or selfie.
- `SpaPromoClient` is browser-native Chromium loaded from the central HTTPS
  origin; local bridge, local web server and WebSocket routes are absent.
- While active, the client keeps exactly one HTTP long-poll request to the
  fixed-name mDNS ESP32 with a 10-second timeout and opens the next immediately
  after an event or timeout.
- The managed kiosk pre-authorizes the central origin for Local Network Access.
  ESP32 permits that exact origin through CORS, handles OPTIONS for the
  Authorization request and validates one manually provisioned Bearer secret
  that stays out of URLs and logs.
- The configuration UI enumerates the browser-visible video-input devices,
  previews the operator-selected camera and remembers that selection while the
  browser retains its device identity.
- Camera disconnect, reconnect or movement to another USB port causes device
  rediscovery. If the remembered device is no longer available, the client
  remains in local advertising and prompts the operator to select from the
  currently available video inputs instead of silently binding an unrelated
  camera or leaving capture broken.
- A clearly identified test-trigger control enters the same local trigger
  acceptance path as the ESP32 event and therefore obeys the same
  capture/search/cooldown overlap rules.
- Physical and test triggers remain distinguishable in request metadata.
- The ring buffer covers the configured pre-trigger interval and produces one
  fresh reference series for the request.
- BlazeFace Full-range uses its browser runtime and a separate release-versioned
  model asset. TensorFlow.js and another project-selected ML runtime are absent;
  YuNet 2026may FP32 may replace BlazeFace only after concrete technical
  incompatibility, never as a parallel implementation or generic abstraction.
- Frames are traversed from earliest pre-trigger to latest post-trigger; client
  processing stops at occurrence 20 and the request preserves those first
  occurrences in frame/detector order.
- The client does not rank, top-5, authoritatively quality-gate, track, cluster
  or deduplicate proposal occurrences, and it does not create embeddings or
  search commercial Photos.
- Each crop is the centered square
  `1.2 × max(bbox_width, bbox_height)`, clipped to the source frame without
  alignment, landmark normalization or upscaling. Crops larger than 512 pixels
  on the long side are proportionally downscaled and encoded as ordinary sRGB
  JPEG without EXIF/source metadata.
- JPEG quality is one dropdown with exactly `0.7`, `0.75`, `0.8`, `0.85`, `0.9`
  and `0.95`, defaults to `0.85`, persists in kiosk-profile `localStorage`,
  applies from the next Attempt and is included in its manifest.
- One ready series produces one synchronous `multipart/form-data` request with
  a versioned JSON manifest and one JPEG part per occurrence. The manifest
  contains only the PRD FR-CAP-17 identity, timing, camera and occurrence
  fields and explicitly omits its listed secret, СПА, geometry and source-frame
  fields.
- The server rejects a total request body larger than `20 MiB` with HTTP `413`
  before domain admission. No separate aggregate-pixel, per-JPEG-byte or
  manifest-size caps and no oversize domain outcome are introduced. Frames
  above the deployment-configured camera maximum are downscaled before the ring
  buffer/detector path.
- A zero-proposal request retains the attempt correlation and client timings;
  server admission creates the core Attempt and explicit non-success outcome.
- New events are ignored during capture/search and successful cooldown.
- A timeout, network error or stale response is discarded; retry requires a new
  reference capture.
- Unsuccessful processing returns directly to advertising without success
  cooldown.
- Server-communication failure shows
  `Попытка связи с сервером была не успешна в hh:mm:ss` as small
  non-blocking text for 5–10 seconds in an easy non-obstructive location; a
  newer message may replace it immediately.
- The display browser runs sandboxed under a non-privileged OS user, and pilot
  runtime administration retains key-only SSH access.

## Edge and Failure Behavior

- If no usable camera is selected or available, no capture/search attempt
  starts; local advertising remains available and the configuration UI exposes
  the recoverable camera-selection state.
- An ESP32 timeout is an ordinary continuation point. Sensor unavailability
  leaves the client in local advertising without adding a fallback transport,
  local bridge or durable sensor queue.
- BlazeFace model load/validation failure leaves the client in advertising with
  a recoverable operator-visible error and does not silently activate YuNet.
- Missing optional audio or animation assets do not block capture or a valid
  result.
- Restarted realtime work is not replayed from a durable queue.
- Advertising remains locally available when the already loaded client
  encounters central-server unavailability. Reload or restart while the central
  HTTPS origin is unavailable is not required to restore advertising.
- Delivery of a client-only offline attempt record is best-effort and may be
  lost after short local expiry or browser restart.
- Exact endpoint path, multipart part naming/serialization and machine outcome
  names remain downstream SDD decisions. Exact camera input dimensions remain a
  site-configuration choice, not a design/tasking gate.

## Verification Targets

- PRD AC-14, AC-21, AC-23..26 and the capture portion of AC-01.
- A more-than-20-occurrence fixture proves chronological first-20 stop/order;
  a zero-occurrence fixture proves manifest-only submission.
- Crop/JPEG/manifest fixtures prove the accepted geometry, quality options,
  structural limits and explicit field omissions. A transport fixture proves
  that a body larger than `20 MiB` returns `413` without core Attempt admission
  or an oversize domain outcome.
- Central-origin Chromium integration proves managed Local Network Access,
  exact-origin CORS/OPTIONS/Bearer handling and continuous one-request
  10-second mDNS long-polling.
- Disconnect and reconnect the configured USB camera, including through another
  USB port, then prove that the refreshed device list allows preview and
  explicit reselection without breaking local advertising.
- Prove that the ESP32 event and the configuration UI test trigger exercise the
  same trigger-acceptance and overlap behavior.
- PRD NFR-SEC-03 evidence for key-only SSH and sandboxed non-privileged display
  browser execution.
- Overlap, stale response, timeout and central-unavailable flows retain safe
  display state.
- Server-communication failure notice is visible for 5–10 seconds without
  blocking advertising; latest notice may replace the prior one.

## Clarifications

### 2026-07-25 — USB camera selection, LAN sensor and test trigger

- The pilot camera is expected to be a browser-visible USB UVC-style webcam;
  its exact model remains open until site validation.
- The client configuration UI must enumerate available video inputs, allow
  preview and explicit selection, and recover through rediscovery/reselection
  after disconnect, reconnect or a USB-port change.
- The passage sensor is expected to be an autonomous ESP32 on the same local
  network as `SpaPromoClient`.
- The client configuration UI includes a clearly identified test-trigger
  control that uses the same local trigger-acceptance path as the physical
  sensor.

### 2026-07-29 — Browser-native client proposal contract

- The single client route is browser-native Chromium loaded from the central
  HTTPS origin. ESP32 uses fixed-name mDNS and authenticated 10-second HTTP
  long-polling; local bridge, local web server and WebSocket are excluded.
- BlazeFace Full-range is the only implemented proposal detector. YuNet is a
  sequential fallback after concrete incompatibility, not a parallel runtime.
- Detection stops after the first 20 chronological occurrences. Crops,
  configurable JPEG encoding and the synchronous multipart request follow the
  accepted PRD FR-CAP-15..17 contract.
- The total request-body transport limit is `20 MiB`; exceeding it returns
  `413` before domain admission and creates no oversize domain outcome.
  Camera-input downscaling is deployment/site configuration.
- A representative benchmark is not required before design or tasking.
