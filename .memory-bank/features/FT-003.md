# FT-003 — Sensor-triggered Capture

**Epic:** [EP-002 — Automatic Promo and QR Continuation](../epics/EP-002.md)

## Outcome

A participant's passage starts one fresh, bounded reference capture without
participant input. The central-origin Chromium client submits the first at most
20 chronological BlazeFace occurrences through one structurally bounded
multipart request while overlap, stale work and central-runtime outages cannot
replace the safe local-advertising state.

## Requirements

- `REQ-CAP-001`, `REQ-CAP-002`, `REQ-UX-004`, `REQ-REL-001`,
  `REQ-PERF-001`.
- Cross-cutting: `REQ-DIAG-001`, `REQ-SEC-001`, `REQ-SEC-002`,
  `REQ-REL-003`, `REQ-ARCH-001`.
- Registry: [.memory-bank/requirements.md](../requirements.md).

## Use Cases

- Maintain a short camera ring buffer while local advertising is visible.
- In the client configuration UI, inspect the currently available USB UVC and
  other browser-visible video inputs, preview them and select the camera used
  for reference capture.
- In authenticated server Admin settings, read the always-visible current token
  for the named kiosk, then manually copy it into that kiosk's central-token
  configuration field for persistence in its managed browser profile.
- Receive passage events from one autonomous ESP32 sensor on the same local
  network as the client through one authenticated 10-second HTTP long-poll at a
  time to its fixed mDNS `.local` name.
- Start the same capture path from an explicit test-trigger control in the
  client configuration UI without requiring the physical sensor.
- Use one sensor event to form the configured pre/post-trigger reference series.
- Traverse the ready series chronologically with BlazeFace Full-range, preserve
  its occurrence order within a frame and stop as soon as occurrence 20 is
  found.
- Crop and encode the first at most 20 occurrences and submit their manifest
  and JPEG parts in one synchronous multipart request.
- Select one of the six accepted JPEG quality values on the
  configuration/debug page for application from the next Attempt.
- Submit attempt metadata without crops when the detector returns no proposals.
- Prevent another trigger from starting capture while capture/search/cooldown
  owns the active attempt.
- Recover to local advertising after camera, network, service or browser failure.

## Acceptance Criteria

### FT-003-AC-001 — Automatic bounded attempt start

- REQ: REQ-CAP-001
- Observable criterion: A physical passage or clearly labelled test trigger
  enters the same capture path without participant action, retains distinct
  trigger-source metadata, forms one fresh configured pre/post-trigger series
  from the active ring buffer and cannot overlap capture/search/success
  cooldown.
- Verification: Exercise physical and test triggers in idle and busy states and
  compare request metadata, series freshness and ignored-event behavior.

### FT-003-AC-002 — Recoverable camera selection

- REQ: REQ-CAP-001, REQ-REL-001
- Observable criterion: The configuration UI lists understandable browser-
  visible camera labels, previews and remembers explicit selection; disconnect,
  reconnect or USB-port change keeps advertising active and requires explicit
  reselection instead of arbitrary substitution. Input above the site maximum
  is downscaled before ring-buffer/detector work.
- Verification: Run camera list/preview selection, disconnect/reconnect/port-
  move and oversized-input fixtures and inspect advertising plus captured input
  dimensions.

### FT-003-AC-003 — Central-origin authenticated sensor route

- REQ: REQ-CAP-001, REQ-SEC-001, REQ-SEC-002
- Observable criterion: Browser-native Chromium loads from the central HTTPS
  origin and, while active, holds exactly one authenticated 10-second HTTP
  long-poll to the fixed-name mDNS ESP32, immediately continuing after event or
  timeout. Managed Local Network Access, exact-origin CORS/OPTIONS and the
  manually provisioned Bearer secret work without secret leakage; no local
  bridge, local web server or WebSocket route exists.
- Verification: Integrate managed Chromium with ESP32, count concurrent/renewed
  polls, inspect CORS preflight and authorization behavior, and scan URLs/logs
  plus runtime topology for forbidden routes or secrets.

### FT-003-AC-004 — Chronological BlazeFace proposals

- REQ: REQ-CAP-002, REQ-ARCH-001
- Observable criterion: MediaPipe BlazeFace Full-range uses its browser runtime
  and separate release-versioned model; chronological traversal preserves
  detector order and stops immediately at occurrence 20. The client performs
  no ranking, top-5 selection, authoritative quality gating, tracking,
  clustering, deduplication, embeddings or commercial-photo search; YuNet can
  replace BlazeFace only after concrete incompatibility, never in parallel or
  behind a generic detector abstraction. Page startup loads the pinned runtime
  and model, performs one discarded synthetic-image inference, and reuses that
  detector for later reference series in the loaded page.
- Verification: Use more-than-20 and repeated-person fixtures, inspect ordered
  emitted proposals and dependency/runtime composition, prove startup warm-up
  precedes the first reference series, and inject model-load failure to confirm
  recoverable advertising without silent fallback.

### FT-003-AC-005 — Crop and JPEG contract

- REQ: REQ-CAP-002
- Observable criterion: Every occurrence crop is a clipped centered square of
  side `1.2 × max(bbox_width, bbox_height)`, never upscaled or aligned; a long
  side above 512 pixels is proportionally downscaled and encoded as sRGB JPEG
  without EXIF/source metadata.
- Verification: Run boundary crop/downscale/no-upscale/metadata fixtures for
  occurrences at the image edges and above/below the resize threshold.

### FT-003-AC-006 — Server-side structurally bounded admission

- REQ: REQ-CAP-002, REQ-DIAG-001
- Observable criterion: The realtime boundary strictly validates the versioned
  manifest allow-list, relational occurrence fields and ordered
  `crop_000..crop_019` JPEG parts; a valid zero-occurrence manifest-only request
  creates one core Attempt with explicit non-success. A body larger than
  `20 MiB` receives HTTP `413` before domain admission and creates neither a
  core Attempt nor an oversize domain outcome; no extra aggregate-pixel,
  per-JPEG-byte or manifest-size cap is introduced.
- Verification: Submit valid and invalid boundary requests directly to the real
  endpoint, test both sides of `20,971,520` bytes and inspect Attempt
  persistence and idempotency.

### FT-003-AC-007 — Fresh retry and failure cooldown semantics

- REQ: REQ-CAP-001, REQ-UX-004, REQ-REL-001
- Observable criterion: Timeout, network error and stale response cannot
  replace a newer display state; retry requires a fresh capture. Any
  unsuccessful attempt returns directly to advertising and permits a fresh
  attempt without starting success cooldown.
- Verification: Inject timeout, disconnect, late response, insufficient-result
  and processing-failure sequences and assert state order, discarded work and
  immediate fresh-capture eligibility.

### FT-003-AC-008 — Safe degraded advertising and recovery

- REQ: REQ-UX-004, REQ-REL-001, REQ-DIAG-001
- Observable criterion: Missing camera, sensor/service unavailability,
  BlazeFace load failure and missing optional assets leave or return the loaded
  client to usable local advertising with recoverable operator feedback.
- Verification: Inject every named dependency failure, observe advertising and
  recovery UI, and confirm missing optional assets never block capture or a
  valid result.

### FT-003-AC-009 — Sandboxed non-privileged kiosk browser

- REQ: REQ-SEC-001
- Observable criterion: The display browser runs sandboxed under the non-
  privileged autologin `display` OS user without `--no-sandbox`, and that user
  has no `sudo`, Docker-group or deployment-secret access.
- Verification: Inspect the effective Chromium process identity, sandbox flags
  and display-user privileges on the pilot host.

### FT-003-AC-010 — One-clock latency contribution

- REQ: REQ-PERF-001, REQ-CAP-002
- Observable criterion: The capture/proposal path supplies monotonic markers
  from `reference_series_ready_at` through request start/response so the joint
  controlled run can require the same 19 of 20 correct attempts to show a fully
  visible QR in under 10 seconds, including local processing and request send.
- Verification: Collect the three required client markers and reconcile their
  monotonic ordering/durations with the controlled 20-attempt acceptance data.

### FT-003-AC-011 — Central runtime independent of display

- REQ: REQ-REL-001
- Observable criterion: Backend, background-worker and realtime roles start and
  remain operational without a KDE session, Chromium process or logged-in
  `display` OS-user session; stopping or crashing the local display session does
  not stop central server processing or readiness.
- Verification: Start the central runtime with no display session, prove its
  role readiness, one authenticated backend request, one queued Photo-state
  transition and one fresh realtime admission, then start and terminate the
  display session and assert that all central roles remain available throughout.

### FT-003-AC-012 — Automatic Chromium recovery

- REQ: REQ-REL-001
- Observable criterion: When the central HTTPS origin is reachable, terminating
  Chromium or crashing the display client causes it to restart and reload
  automatically without operator action, discard prior personalized result,
  reference-frame, QR/session-token and active-Attempt state, retain the
  configured central display-client credential and return to usable local
  advertising. No advertising recovery is promised while a restarted client
  cannot reach the central origin.
- Verification: With the origin reachable, kill the Chromium/client process
  during advertising and during an active/result state, observe automatic
  process replacement and reload, and assert advertising, retained central
  display-client configuration plus absence of the prior personalized
  result/frame/QR-session-token state after recovery.

### FT-003-AC-013 — Verifiable recovery procedure

- REQ: REQ-REL-003
- Observable criterion: An authorized operator has a documented procedure with
  explicit preconditions, recovery steps and success checks for both browser
  failure and an ordinary central-runtime/server restart with intact primary
  PostgreSQL/MinIO volumes; it states the accepted no-offline-start and
  irreversible-primary-loss limits.
- Verification: Starting from each named failure state, follow only the
  documented procedure and record its checks proving restored central-role
  readiness, automatic Chromium reload once HTTPS is reachable, usable local
  advertising and preserved intact-volume durable state.

### FT-003-AC-014 — Kiosk-profile JPEG quality

- REQ: REQ-CAP-002
- Observable criterion: The configuration/debug UI offers exactly qualities
  `0.7`, `0.75`, `0.8`, `0.85`, `0.9`, `0.95`, defaults to `0.85`, persists the
  selected value in the managed kiosk browser profile and applies and records
  it from the next Attempt without mutating an active Attempt.
- Verification: Reload the client and exercise every accepted quality value,
  the default and a change during an active Attempt, then inspect the next
  emitted manifest.

### FT-003-AC-015 — Client multipart request formation

- REQ: REQ-CAP-002, REQ-DIAG-001
- Observable criterion: One ready series creates exactly one synchronous
  `multipart/form-data` request with the versioned manifest allow-list and one
  `crop_NNN` JPEG part per first-at-most-20 occurrence in chronological order;
  zero occurrences send the manifest only, and the display token appears only
  in the Authorization header.
- Verification: Capture real browser requests from more-than-20, ordinary and
  zero-occurrence series and compare fields, explicit omissions, part names,
  ordering, content types and credential placement.

### FT-003-AC-016 — Non-blocking server-communication notice

- REQ: REQ-UX-004
- Observable criterion: A server-communication failure shows
  `Попытка связи с сервером была не успешна в hh:mm:ss` non-blockingly for
  5–10 seconds in the easiest non-obstructive location; a newer notice replaces
  the prior one immediately without changing advertising or retry semantics.
- Verification: Inject successive communication failures, time the visible
  interval and replacement, and assert advertising plus fresh-capture
  eligibility remain usable.

### FT-003-AC-017 — Managed Local Network Access policy

- REQ: REQ-SEC-001, REQ-SEC-002
- Observable criterion: The managed Chromium kiosk profile pre-authorizes
  exactly the central Face Moment origin through
  `LocalNetworkAccessAllowedForUrls`, with no wildcard or unrelated origin.
- Verification: Inspect the effective managed policy and prove the real
  central-origin browser can reach the ESP32 fixture while an unlisted origin
  cannot rely on that pre-authorization.

### FT-003-AC-019 — Private internal port topology

- REQ: REQ-SEC-001
- Observable criterion: Only the non-production HTTPS edge is externally
  reachable; PostgreSQL, MinIO and backend/worker/realtime internal role ports
  remain private and are never exposed through the client flow.
- Verification: Compare the source-managed bind/publish configuration with an
  external port scan of the pilot host.

### FT-003-AC-020 — Manual central-token kiosk handoff

- REQ: REQ-SEC-001, REQ-REL-001
- Observable criterion: An authenticated `operator|developer` manually copies
  the current token shown for the named kiosk by `GET /staff/display-clients`
  into that kiosk's central-token configuration field; the value survives page
  reload and Chromium restart in the managed profile and authenticates only as
  the display-client Bearer credential. Reset invalidates the old value and
  requires another manual copy; no push, pairing or deployment-policy secret
  injection path exists.
- Verification: Perform the real-browser handoff, authenticate after reload
  and restart, reset and repeat the copy, then scan runtime/configuration paths
  for leakage or an automatic handoff.

## Edge and Failure Behavior

- If no usable camera is selected or available, no capture/search attempt
  starts; local advertising remains available and the configuration UI exposes
  the recoverable camera-selection state. Covered by `FT-003-AC-002` and
  `FT-003-AC-008`.
- An ESP32 timeout is an ordinary continuation point. Sensor unavailability
  leaves the client in local advertising without adding a fallback transport,
  local bridge or durable sensor queue. Covered by `FT-003-AC-003` and
  `FT-003-AC-008`.
- BlazeFace model load/validation failure leaves the client in advertising with
  a recoverable operator-visible error and does not silently activate YuNet.
  Covered by `FT-003-AC-004` and `FT-003-AC-008`.
- Missing optional audio or animation assets do not block capture or a valid
  result. Covered by `FT-003-AC-008`.
- Restarted realtime work is not replayed from a durable queue. Covered by
  `FT-004-AC-008`.
- The central runtime starts and continues without a local display session.
  Covered by `FT-003-AC-011`.
- Chromium/browser failure recovers automatically when the central HTTPS origin
  is reachable, without restoring personalized client state. Covered by
  `FT-003-AC-012`.
- The server always shows each kiosk's current display-client token to an
  authenticated Admin. Transfer into the intended kiosk profile is manual; a
  reset requires the Admin to repeat that copy, while no push, pairing or
  deployment-secret injection path exists. The configured central credential
  survives page/browser restart as kiosk configuration and is not the
  personalized QR/session token discarded by recovery. Covered by the linked
  Display Client Access contract and `FT-003-AC-020` plus `FT-003-AC-012`.
- Advertising remains locally available when the already loaded client
  encounters central-server unavailability. Reload or restart while the central
  HTTPS origin is unavailable is not required to restore advertising.
  Covered by `FT-003-AC-008`; the cold-start limitation is an accepted PRD
  `NFR-REL-02` condition.
- No offline-metadata delivery path is required or planned for FT-003. The PRD
  allowance for bounded best-effort client-only metadata remains optional and
  participant flow never depends on it.
- Browser and intact-volume restart recovery remains an operator-executable,
  bounded procedure rather than a backup or primary-storage-loss guarantee.
  Covered by `FT-003-AC-013`.
- Exact endpoint paths, multipart part naming/serialization, validation and
  machine outcome names are fixed by the linked sensor/realtime contracts.
  Exact camera input dimensions remain a site-configuration choice, not a
  product-decomposition blocker. Product acceptance is covered by
  `FT-003-AC-002`, `FT-003-AC-006`, `FT-003-AC-015` and the SDD Design Gate
  below.

## Verification Targets

- `FT-003-AC-001..020`, preserving PRD AC-14, AC-21, AC-23..26 and the
  capture portion of AC-01.
- A more-than-20-occurrence fixture proves chronological first-20 stop/order;
  a zero-occurrence fixture proves manifest-only submission.
- Crop/JPEG/manifest fixtures prove the accepted geometry, quality options,
  structural limits and explicit field omissions. A transport fixture proves
  that a body larger than `20 MiB` returns `413` without core Attempt admission
  or an oversize domain outcome.
- Central-origin Chromium integration proves managed Local Network Access,
  exact-origin CORS/OPTIONS/Bearer handling and continuous one-request
  10-second mDNS long-polling.
- Admin/kiosk integration proves repeated authorized server-settings reads show
  the same current token, a photographer cannot read it, manual copy into the
  named kiosk authenticates after reload and Chromium restart, and reset
  requires manual replacement without token leakage or an automatic handoff.
- Disconnect and reconnect the configured USB camera, including through another
  USB port, then prove that the refreshed device list allows preview and
  explicit reselection without breaking local advertising.
- Prove that the ESP32 event and the configuration UI test trigger exercise the
  same trigger-acceptance and overlap behavior.
- PRD NFR-SEC-03 evidence for sandboxed non-privileged display browser
  execution.
- Overlap, stale response, timeout and central-unavailable flows retain safe
  display state.
- Starting and operating the central runtime without the display session proves
  PRD NFR-REL-01; forced Chromium/client termination proves automatic recovery
  under the reachable-origin condition in NFR-REL-02.
- An operator executes the documented browser and intact-volume restart
  recovery procedure and retains the procedure plus check results as evidence.
- Server-communication failure notice is visible for 5–10 seconds without
  blocking advertising; latest notice may replace the prior one.

## Clarifications

### 2026-07-25 — USB camera selection, LAN sensor and test trigger

- The pilot camera is expected to be a browser-visible USB UVC-style webcam;
  its exact model remains open until site validation.
- The client configuration UI must enumerate available video inputs, allow
  preview and explicit selection, and recover through rediscovery/reselection
  after disconnect, reconnect or a USB-port change.
- The passage sensor is expected to be an autonomous ESP32 on the same local
  network as `SpaPromoClient`.
- The client configuration UI includes a clearly identified test-trigger
  control that uses the same local trigger-acceptance path as the physical
  sensor.

### 2026-07-29 — Browser-native client proposal contract

- The single client route is browser-native Chromium loaded from the central
  HTTPS origin. ESP32 uses fixed-name mDNS and authenticated 10-second HTTP
  long-polling; local bridge, local web server and WebSocket are excluded.
- BlazeFace Full-range is the only implemented proposal detector. YuNet is a
  sequential fallback after concrete incompatibility, not a parallel runtime.
- Detection stops after the first 20 chronological occurrences. Crops,
  configurable JPEG encoding and the synchronous multipart request follow the
  accepted PRD FR-CAP-15..17 contract.
- The total request-body transport limit is `20 MiB`; exceeding it returns
  `413` before domain admission and creates no oversize domain outcome.
  Camera-input downscaling is deployment/site configuration.
- A representative benchmark is not required before design or tasking.
