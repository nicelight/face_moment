# FT-004 — Scoped Realtime Search and Result Assembly

**Epic:** [EP-002 — Automatic Promo and QR Continuation](../epics/EP-002.md)

## Outcome

One current client proposal request produces either a valid four-teaser
personalized result with truthful `N` or an explicit non-success outcome, using
exact scoped search and the accepted best-effort group semantics.

## Requirements

- `REQ-SRCH-001`, `REQ-SRCH-002`, `REQ-SRCH-003`, `REQ-CAP-003`,
  `REQ-PERF-001`.
- Cross-cutting: `REQ-REL-001`, `REQ-DIAG-001`, `REQ-SEC-001`,
  `REQ-ARCH-001`.
- Registry: [.memory-bank/requirements.md](../requirements.md).

## Use Cases

- On the server, select at most five highest-quality received proposals and
  search each selected detection independently.
- Search only compatible searchable commercial inventory for the token-bound СПА
  and operator-selected active `visit_date`.
- Assemble four unique valid teaser photos and the complete valid unique-photo
  union used for `N`.

## Acceptance Criteria

### FT-004-AC-001 — Compatible scoped exact search

- REQ: REQ-SRCH-001, REQ-SRCH-003
- Observable criterion: A pre-warmed serving pipeline preserves its native
  processing path, and exact cosine search filters compatible `ready` inventory
  by immutable revision, token-derived СПА and operator-selected active
  `visit_date` before comparison; optional time filtering is used only with
  confirmed clock quality.
- Verification: Query mixed revisions, СПА, dates and readiness states and
  assert only the compatible active scope participates in exact search.

### FT-004-AC-002 — Server-authoritative detection selection

- REQ: REQ-SRCH-002
- Observable criterion: The server ranks/selects at most five received
  occurrences, searches each selected detection independently, applies query-
  quality plus calibrated reference threshold, and uses neither top-1/top-2
  margin, tracking, identity clustering nor cross-pipeline linking. Repeated
  occurrences of one person remain allowed.
- Verification: Use ordered, repeated-person and low-quality proposal fixtures
  to inspect selected detections and independent search/gate decisions.

### FT-004-AC-003 — Truthful four-teaser result and `N`

- REQ: REQ-CAP-003
- Observable criterion: pHash ranks only threshold-valid candidates; success
  contains four unique `photo_id` teaser values, and `N` is the cardinality of
  the complete unique threshold-valid union across processed detections.
- Verification: Run candidate-pool fixtures containing repeated Photo matches,
  weak matches and diversity ties and reconcile teasers plus `N` with the full
  valid union.

### FT-004-AC-004 — Joint controlled-attempt correctness

- REQ: REQ-PERF-001, REQ-CAP-003
- Observable criterion: In at least 19 of the same 20 controlled attempts that
  pass the QR latency gate, every teaser and every `photo_id` counted in `N`
  belongs to a pilot participant represented by a processed selected detection;
  incomplete group-member coverage alone is not failure.
- Verification: Manually ground-truth all four teasers and the complete issued
  result union for each controlled attempt and evaluate the joint pass set.

### FT-004-AC-005 — Token-bound public search boundary

- REQ: REQ-SEC-001
- Observable criterion: Realtime requests are rate-limited; the server derives
  `spa_id` only from the stored hash of the authorization token, rejects any
  client attempt to override it and never writes the token to logs.
- Verification: Exercise valid, absent, foreign, body-overridden and rate-
  limited requests and scan persisted/searchable logs for token material.

### FT-004-AC-006 — Explicit no-success paths

- REQ: REQ-SRCH-003, REQ-CAP-003
- Observable criterion: Missing active date prevents search with diagnostic
  evidence; fewer than four unique valid teasers produces an explicit non-
  success; ongoing uploads may expose only the currently compatible `ready`
  subset without an ingest-group readiness gate; one Photo matching multiple
  detections contributes to `N` once.
- Verification: Exercise missing-date, partial-inventory, insufficient-result
  and repeated-Photo fixtures and inspect typed outcomes, evidence and `N`.

### FT-004-AC-007 — Singleton admission and typed busy

- REQ: REQ-REL-001, REQ-DIAG-001
- Observable criterion: Exactly one admitted realtime request may own the
  inference slot under one server deadline. A concurrent valid request is
  admitted as its own core Attempt and returns a typed `busy` outcome without
  waiting or starting inference; it is not stored in a waiter queue, and a
  later fresh request may acquire the released slot.
- Verification: Hold the slot with one instrumented request, submit a second
  valid request concurrently and assert its persisted Attempt, `busy` response
  before the owner releases and zero inference calls; then release or deadline
  the owner and prove that the busy request is not resumed and only a fresh
  request starts the next inference.

### FT-004-AC-008 — Restart interrupts without replay

- REQ: REQ-REL-001, REQ-DIAG-001
- Observable criterion: Realtime startup closes every pre-restart core Attempt
  still in `accepted|searching` as `interrupted`; it neither resumes inference
  nor publishes a result/session from that stale reference work. Only a fresh
  capture/request can start new realtime processing after restart.
- Verification: Restart the realtime service during both pre-slot and active-
  inference states, then inspect Attempt transitions, inference invocation
  counts and result/session records to prove interruption without replay or
  late publication before submitting one fresh request.

## Edge and Failure Behavior

- Missing active date prevents search and records diagnostic evidence. Covered
  by `FT-004-AC-006`.
- Search uses all currently `ready` compatible photos for the active СПА/date;
  while upload/processing continues, observing a partial current-day set is
  acceptable and does not require an ingest-group readiness gate.
  Covered by `FT-004-AC-001` and `FT-004-AC-006`.
- Fewer than four unique valid teaser photos is a non-success outcome. Covered
  by `FT-004-AC-006`.
- One photo matching multiple selected detections contributes to `N` once.
  Covered by `FT-004-AC-003` and `FT-004-AC-006`.
- A concurrent admitted request receives typed `busy` and never waits for the
  singleton inference slot. Covered by `FT-004-AC-007`.
- Restart interrupts unfinished realtime work without replaying it or
  publishing a late result. Covered by `FT-004-AC-008`.

## SDD Design Gate

Complete. Server search remains owned by `processing`; `promo` owns singleton
orchestration, candidate/result assembly and result-session publication. The
direct subject specs fix the immutable active-search context, exact search,
candidate pools, typed outcomes and restart behavior; client and joint
correctness verification use the linked realtime test contract. Realtime loads
only the committed validated revision from operator-managed read-only assets
and fails closed before Attempt admission on mismatch. The client supplies the
first at most 20 chronological occurrences, while ranking, at-most-five
selection, validation, embeddings and independent search remain
server-authoritative.
