# FT-001 — Photographer Batch Ingest

**Epic:** [EP-001 — Fresh Searchable Inventory](../epics/EP-001.md)

## Outcome

An authenticated photographer can submit ready JPEGs for one СПА and one
authoritative working date, understand validation outcomes, and freeze a clean,
duplicate-free commercial-photo manifest for processing.

## Requirements

- `REQ-ING-001`, `REQ-ING-002`, `REQ-ING-003`.
- Cross-cutting: `REQ-SEC-001`, `REQ-ARCH-001`.
- Registry: [.memory-bank/requirements.md](../requirements.md).

## Use Cases

- Create a batch and select СПА plus authoritative `visit_date`.
- Upload multiple ready JPEG files through the authenticated HTTPS application.
- Review accepted, rejected, warning and duplicate outcomes before confirming.
- Confirm an immutable manifest and observe the processing handoff.

## Acceptance Criteria

- Invalid, unsupported or undecodable files are visibly rejected before
  confirmation.
- Mixed EXIF dates may warn but never rewrite `visit_date` or split the batch.
- Confirmation freezes the accepted manifest and `confirmed_at`.
- A same-СПА/date SHA-256 duplicate in any batch is deleted and reported and
  creates no new manifest member, `photo_id`, object, job or downstream result.
- Direct authenticated JPEG upload is the only pilot ingest channel.
- Upload uses the public HTTPS application boundary; PostgreSQL, object storage
  and internal service ports are not exposed through the photographer flow.

## Edge and Failure Behavior

- Pre-confirmation rejects and duplicates never enter metric population.
- Repeated upload is idempotent within the PRD duplicate scope.
- Yandex Disk, RAW, OAuth, Telegram and EXIF-based auto-split remain post-pilot.
