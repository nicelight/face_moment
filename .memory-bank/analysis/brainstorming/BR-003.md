## Problem Space

Подтверждено пользователем только исходное направление обсуждения:

- главный пользователь logging/diagnostics — разработчик приложения;
- найти и запланировать качественное browser-side и server-side logging;
- использовать собранные данные для анализа качества работы Face Moment;
- улучшать систему путём подбора оптимальных параметров;
- просматривать и искать логи на страницах самого приложения.

Первая версия должна дать разработчику простой связанный путь от отдельной
Promo/QR attempt и её browser/server logs к performance breakdown, group-search
решениям, ручной разметке и объяснимым рекомендациям по face threshold и quality
gates. Решение остаётся внутри существующих backend/PostgreSQL и не превращается
в отдельную observability или test-management platform.

## Goals

Подтверждённые developer investigation goals первой версии:

- разобрать одну неуспешную Promo/QR attempt end-to-end;
- локализовать performance bottleneck при нарушении `<10 s`;
- калибровать face threshold и сравнивать pipelines на размеченных cases;
- исследовать best-effort group result, включая выбранные detections,
  пропущенных участников, candidate pools, teaser и `N`.
- выполнять per-person/per-detection ground-truth annotation: разработчик
  связывает detection с участником и отмечает правильные, ложные и пропущенные
  совпадения.
- анализировать и подбирать в первой версии только face-match threshold,
  сравнение SFace/Buffalo M и input quality gates по размеру лица, detection
  confidence, blur, brightness и pose.
- рассчитывать предлагаемые threshold/quality-gate values и показывать
  ожидаемое влияние на `correct`, `false` и `missed`, оставляя применение
  serving settings ручным действием разработчика.
- показывать одновременно три recommendation profiles: «Лучшее совпадение
  лица», «Баланс» и «Минимум пропусков лиц».
- предоставить разработчику три отдельные страницы: `Attempts`, `Log Explorer`
  и `Calibration`.

С разрешения пользователя к первой версии также добавлены два сценария с малым
incremental scope:

- сравнение regression до/после release или parameter/config change;
- воспроизведение сложного case через уже собираемые manifest, versions,
  parameters, timestamps и diagnostic artifact references.

## Constraints

Подтверждено пользователем:

- следовать KISS и не строить внутри приложения сложную test-management или
  experimentation system;
- добавлять только logging/diagnostic capabilities с небольшим и понятным
  incremental implementation cost;
- реальные имена pilot-тестировщиков разрешено сохранять в diagnostic
  annotations;
- pseudonymization, отдельный subject registry и сложное управление datasets не
  нужны для текущего pilot;
- searchable browser/server logs используют существующий backend и PostgreSQL,
  без отдельного observability datastore;
- technical logs хранятся 30 дней, attempts и diagnostic bundles — 90 дней;
- вручную отобранные calibration cases и annotations хранятся до явного
  удаления;
- session replay, images, tokens и request bodies не сохраняются внутри logs.

## Raw Ideas

Ниже рассмотренные developer investigation scenarios; итоговый выбор указан в
`Selected Directions`:

1. Разобрать одну неуспешную Promo/QR попытку по времени или
   `diagnostic_session_id`: увидеть общий browser/server timeline, ошибку,
   применённые параметры и связанный diagnostic bundle.
2. Найти performance bottleneck при нарушении `<10 s`: разложить задержку на
   capture, upload/network, queue wait, inference, vector search, response и
   browser render/QR visibility, затем перейти к самым медленным attempts.
3. Проверить regression после release или изменения конфигурации: сравнить
   периоды/версии по success rate, no-match, errors и latency, затем открыть
   конкретные отличающиеся cases.
4. Калибровать face threshold или сравнивать pipelines: работать с размеченными
   correct/incorrect/missed cases, score distributions и фактически применённым
   parameter set, не смешивая calibration и validation samples.
5. Разобрать browser/display failure: JS error, `unhandledrejection`, camera или
   sensor failure, network timeout, зависшее state transition, Chromium restart
   либо QR, который сервер вернул, но display не показал.
6. Разобрать медленный или сломанный ingest: пройти от batch confirmation через
   preview, face processing и job state до `searchable`, увидеть worker error и
   причину нарушения `ingest_to_searchable`.
7. Исследовать best-effort group result: какие detections были выбраны, почему
   один человек занял несколько slots, кого пропустили, какие photos попали в
   candidate pools, teaser и итоговый `N`.
8. Воспроизвести сложный case: получить redacted manifest с версиями,
   параметрами, timestamps и ссылками на разрешённые diagnostic artifacts для
   локального анализа или benchmark dataset.
9. Выполнить ad-hoc поиск по raw browser/server logs: time range, component,
   severity, message, release и correlation fields, при необходимости включив
   короткий live tail во время controlled test.
10. Проверить общее operational state перед acceptance run: версии процессов,
    готовность pipeline, очередь/background backlog, свободное место, telemetry
    gaps и состояние конкретного `SpaPromoClient`.

Рассмотренные logging backend directions:

- существующий backend + PostgreSQL как KISS-вариант;
- [Grafana Faro](https://github.com/grafana/faro-web-sdk) + Alloy + Loki для
  browser RUM и специализированного log exploration;
- [SigNoz](https://signoz.io/docs/frontend-monitoring/) как self-hosted unified
  logs/traces/metrics stack;
- [ClickStack/HyperDX](https://clickhouse.com/clickstack) для high-cardinality
  observability и session-oriented analysis;
- [OpenSearch Logs Explorer](https://docs.opensearch.org/latest/observing-your-data/exploring-observability-data/discover-logs/)
  для развитого full-text/log analytics.

## Clusters / Themes

### 1. Attempt investigation

Одна attempt связывает browser/server timeline, performance stages, group-search
решения, diagnostic artifacts и ручную разметку.

### 2. Explainable calibration

Face threshold получает три понятных recommendation profiles, а каждый quality
gate анализируется отдельно. Любое применение остаётся ручным.

### 3. Developer-first UI

Три страницы разделяют повседневное расследование attempts, свободный поиск
логов и calibration analysis без создания отдельного test product.

### 4. KISS observability

Existing backend/PostgreSQL остаются ingestion/query/storage boundary. Новый
observability stack не добавляется до измеримой необходимости.

### 5. Bounded sensitive data

Имена разрешены только в manual diagnostic annotations; технические logs не
содержат images, tokens, request bodies или session replay и имеют ограниченный
retention.

## Selected Directions

Пользователь выбрал обязательными для первой версии developer scenarios:

1. Исходный scenario 1 — разбор одной неуспешной Promo/QR attempt.
2. Исходный scenario 2 — поиск performance bottleneck при нарушении `<10 s`.
3. Исходный scenario 4 — калибровка face threshold/сравнение pipelines на
   размеченных cases.
4. Исходный scenario 7 — анализ best-effort group result.

С явного разрешения пользователя фасилитатор добавил два low-incremental-cost
сценария:

5. Исходный scenario 3 — regression comparison до/после release или изменения
   parameter/config set:
   он переиспользует versioned parameters, outcomes и comparison UI сценария
   калибровки.
6. Исходный scenario 8 — воспроизведение case через redacted manifest и уже
   связанные diagnostic artifacts: он переиспользует attempt detail сценария
   расследования.

Границы low-cost дополнений:

- regression comparison не означает отдельную experimentation platform;
- воспроизведение не означает автоматический replay runner или bulk export;
- базовый structured log search является общей capability выбранных сценариев,
  но live tail пока не выбран.

Для calibration и group analysis пользователь выбрал детальную
`per-person/per-detection` разметку вместо только итоговой attempt-level оценки
или исключительно заранее подготовленного эталонного dataset.

Разметка следует KISS:

- разработчик вручную указывает имя участника в diagnostic attempt;
- связывает имя с detection;
- отмечает `correct`, `wrong` или `missed`;
- разметка является частью существующего diagnostic workflow;
- отдельные participant management, pseudonym mapping, experiment management,
  dataset catalog и автоматический replay framework не создаются.

Parameter-tuning scope первой версии ограничен:

- face-match threshold;
- сравнение SFace и Buffalo M;
- quality gates: размер лица, detection confidence, blur, brightness и pose.

Capture window/frame interval, group-selection parameters, CPU/thread settings и
UI/QR timings пока не входят в parameter-tuning scope.

Parameter tuning работает в рекомендательном режиме:

- система вычисляет candidate/recommended values из размеченных данных;
- рядом показывает ожидаемые counts/rates `correct`, `false` и `missed`;
- вместо одной скрыто выбранной optimum показывает три named profiles:
  «Лучшее совпадение лица», «Баланс» и «Минимум пропусков лиц»;
- «Лучшее совпадение лица» минимизирует false matches и при равенстве выбирает
  вариант с большим числом correct matches;
- «Баланс» ищет компромисс между correct, false и missed results;
- «Минимум пропусков лиц» минимизирует missed results и при равенстве выбирает
  вариант с меньшим числом false matches;
- каждая recommendation показывает proposed threshold, counts `correct`,
  `false`, `missed`, precision, recall и размер размеченной выборки;
- три recommendation profiles рассчитываются только для face-match threshold;
- quality gates по face size, detection confidence, blur, brightness и pose
  анализируются независимо друг от друга и получают отдельные простые
  рекомендации без совместного перебора комбинаций;
- отдельная quality-gate recommendation содержит current/proposed value,
  sample size, kept/rejected detections и ожидаемое изменение
  `correct/false/missed`;
- face size и detection confidence используют minimum cutoff, brightness —
  допустимый range, pose — maximum absolute yaw/pitch/roll, а направление blur
  cutoff следует фактической семантике выбранной метрики;
- разработчик явно подтверждает и вручную применяет выбранное значение;
- automatic serving-setting changes запрещены.

Developer UI разделён на три страницы:

- `Attempts` — список attempts, detail/timeline, per-person/per-detection
  annotation, group result и diagnostic artifacts;
- `Log Explorer` — глобальный поиск browser/server logs и переход к связанной
  attempt;
- `Calibration` — pipeline/threshold comparison и отдельные quality-gate
  recommendations.

Logging backend и retention:

- browser/server structured logs сохраняются и ищутся через существующий
  backend и PostgreSQL;
- existing backend является единственным application/query boundary для
  developer pages; конкретный ingestion contract определяется в последующем
  design/spec flow;
- technical logs хранятся 30 дней;
- attempts и diagnostic bundles хранятся 90 дней;
- вручную отобранные calibration cases и annotations хранятся до явного
  удаления;
- session replay не используется;
- images, tokens и request bodies не включаются в log records.

## Rejected Directions

- Отдельные Grafana Faro/Loki, SigNoz, ClickStack/HyperDX или OpenSearch stacks
  в первой версии: они не выбраны из-за KISS и дополнительной эксплуатации.
- Сложная встроенная test-management/experimentation platform.
- Отдельные participant registry, pseudonym mapping и dataset catalog.
- Session replay.
- Automatic application of recommended serving settings.
- Совместная многомерная оптимизация threshold и всех quality gates.
- Live tail как обязательная capability первой версии.
- Bulk diagnostic export и automatic replay runner.
- Images, tokens или request bodies внутри searchable logs.

## Assumptions

- Объём one-SPA pilot позволяет хранить и искать 30-day structured logs в
  PostgreSQL без отдельного log datastore; это следует проверить на реальном
  telemetry volume до target expansion.
- Разработчик вводит имена тестировщиков достаточно последовательно для
  pilot-разметки без отдельного participant registry.
- Вручную сохранённые calibration cases немногочисленны и могут удаляться явно,
  без отдельной lifecycle system.
