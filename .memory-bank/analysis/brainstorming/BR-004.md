## Problem Space

FT-003 currently treats a representative client benchmark as a prerequisite for
choosing the client route, local proposal stack, crop contract, request schema
and hard bounds. The operator has clarified that this is the wrong feature cut:
these reversible pilot design choices should be selected now. Later
implementation evidence may verify the selected route against the existing
`<10 s` acceptance contract, but it must not reopen the design by comparing
multiple implementations or require a representative benchmark before tasking.

The useful decision is therefore one coherent `SpaPromoClient` bundle:

```text
camera + sensor event
→ bounded reference series
→ local occurrence proposals
→ portable crops + metadata
→ one bounded synchronous server request
```

## Goals

- Select one client route instead of building browser and bridge variants.
- Select one local proposal detector/runtime/model/update approach.
- Fix a simple crop format that leaves native server detection/alignment in
  control.
- Fix the smallest useful request envelope and diagnostics metadata.
- Fix protective pilot caps without turning them into ranking or hidden
  top-five selection.
- Keep every choice reversible through an ordinary client release.

## Constraints

Already accepted:

- `SpaPromoClient` owns camera access, reference-series capture, local proposal
  detection, request submission, display state and client timings.
- A browser-visible USB UVC-style camera is selected and previewed explicitly in
  configuration UI; exact hardware remains a site choice.
- The passage sensor is one autonomous ESP32 on the same LAN as the client.
- The local detector returns occurrences only. It does not embed, recognize,
  rank, quality-gate, track, cluster or deduplicate people.
- The detector processes the ready series until it has returned 20 occurrences.
  It then stops processing remaining frames and submits those first 20;
  repeated occurrences of the same person are valid.
- Server-side processing remains authoritative for validation, quality,
  ranking, selection of at most five detections, native alignment, embeddings
  and search.
- Zero proposals use a metadata-only request. Local detection stops at
  occurrence 20 and crops longer than 512 pixels are downscaled. The server
  rejects a request body larger than `20 MiB` with HTTP `413`; this transport
  rejection creates no domain oversize outcome or subset-selection path.
- The ordinary flow does not upload full reference frames.
- The `<10 s` interval includes local detection, crop encoding and upload.
- Central search remains one synchronous HTTPS request/response; no result
  event channel or durable client retry queue is introduced.

## Techniques Used

- Constraint-first option reduction.
- End-to-end failure-path walkthrough.
- KISS value-versus-cost preflight.
- Boundary minimization between Chromium, ESP32 and the central realtime API.
- Reversible-default analysis for crop and payload caps.

No new external research was performed in this brainstorm.

## Raw Ideas

### Client route

1. Browser-native Chromium owns camera, detector, sensor connection, display and
   recovery in one web bundle.
2. A narrow local bridge owns hardware/ML and exposes a local contract to the
   same web bundle.
3. Both routes or a generic device/runtime plugin layer.

The browser route has the smallest deployment and ownership surface. The bridge
adds another process, packaging/update path, restart behavior and local API. It
has value only if the sensor or detector cannot be consumed by the controlled
Chromium runtime.

### ESP32 transport

1. One outstanding HTTP long-poll request from Chromium to an ESP32 endpoint
   published through mDNS.
2. One client-initiated WebSocket to a manually configured ESP32 LAN endpoint.
3. ESP32-to-central-server delivery followed by a second realtime channel back
   to the display.
4. A local bridge accepting a device-specific protocol.

The operator selected HTTP long-poll with a 10-second timeout and mDNS. It
preserves local ownership without a server event channel or local bridge.
`SpaPromoClient` stays on the central HTTPS origin. The managed Chromium kiosk
receives Local Network Access permission for that origin, while the ESP32
permits the exact origin through CORS and handles preflight when Authorization
is used.

### Detector/runtime/model

1. MediaPipe BlazeFace Full-range through its ready browser runtime.
2. YuNet 2026may FP32 as a fallback only if the primary option proves
   technically unusable.
3. Both detectors, TensorFlow.js or a generic multi-runtime abstraction
   implemented in parallel.

The operator selected the first option. It targets multiple faces at distances
up to five meters, requires less project-owned preprocessing/postprocessing and
does not add TensorFlow.js or a separate ML runtime. The fallback is sequential:
it is reconsidered only after concrete technical failure of the primary option.

### Crop shapes

1. A square, centered, padded proposal region that is clipped to the source
   frame, is not locally aligned and is downscaled only when it exceeds the
   accepted maximum.
2. A tight detector bounding box.
3. A large person/frame region.
4. A locally normalized/aligned recognizer input.

A modest padded square preserves enough context for the server-native detector
without uploading full frames or coupling the client to SFace/Buffalo
preprocessing.

### Wire format

1. `multipart/form-data`: one JSON manifest part and one JPEG part per
   occurrence.
2. JSON with base64-encoded crops.
3. Several per-crop requests.
4. A binary custom protocol.

Multipart avoids base64 expansion, preserves one-attempt atomic submission and
uses the existing HTTP/FastAPI boundary without a custom protocol.

### Bounds

1. Bound local work structurally through camera-frame size, first-20 detection
   and maximum crop dimensions.
2. Add a separate complete-request body limit.
3. Rank or truncate locally until the request fits.

The operator selected structural input bounds and originally rejected a
separate body-size failure mode. On 2026-07-29 the operator added one
server-side `20 MiB` complete-request transport limit with HTTP `413`. After
the traversal-level first-20 cap, additional quality ranking/truncation is
still forbidden.

## Clusters / Themes

### One browser-owned client

Camera, proposal inference, sensor health and display state stay in one
Chromium bundle. There is no native hardware/ML bridge. ESP32 trigger delivery
uses direct HTTP long-poll from the browser.

### Release-owned ML

The proposal model is application code/data, not a remotely managed model
platform. Client release identity determines the detector artifact.

### Portable, non-authoritative proposals

Crops preserve context but do not align, recognize or select identities. The
server can still run its native detector/alignment path.

### One bounded admission

One manifest plus at most the first 20 structurally bounded crop parts forms the
request. Detection stops at the accepted first-20 cap; a body larger than
`20 MiB` is rejected by the server with HTTP `413` before domain admission.
There is no domain oversize outcome, quality ranking or hidden top-five
selection.

## Accepted Technical Decision Detail

The browser/sensor route, detector, crop, request and structural-bound sections
below were explicitly selected by the operator. The later `Selected Directions`
section is their authoritative summary.

### 1. Selected browser and sensor route

- Use browser-native Chromium with the existing web bundle.
- Load `SpaPromoClient` from the central Face Moment HTTPS origin; no local web
  server is introduced.
- Use `MediaDevices` for enumeration, preview and capture.
- Resolve the ESP32 through a fixed mDNS `.local` name, for example
  `fm-sensor1.local`.
- Keep exactly one outstanding HTTP long-poll request with a 10-second server
  hold timeout; after an event, timeout or recoverable transport failure, open
  the next request while the client remains active.
- Use a compact versioned response with `sensor_id`, per-boot `boot_id`,
  monotonic `sequence` and `type: passage`.
- Treat receipt on the client as `t=0`; do not subtract ESP32 and client clocks.
- Deduplicate only repeated transport delivery of the same
  `(boot_id, sequence)` in memory. This is not person/capture deduplication.
- Keep retry/backoff and health in memory. No durable sensor queue,
  discovery service or pairing subsystem is introduced.
- Pre-authorize the central HTTPS origin in the managed kiosk through
  `LocalNetworkAccessAllowedForUrls`.
- Configure ESP32 CORS with the exact
  `Access-Control-Allow-Origin: https://<face-moment-origin>` value rather than
  a wildcard.
- Use one manually provisioned sensor `Bearer` secret. The configuration UI
  stores it in the managed kiosk browser profile and sends it only in the
  Authorization header.
- ESP32 handles the browser OPTIONS preflight and validates the Bearer secret.
  The secret never enters a URL or log.
- Do not add pairing, automatic rotation, certificate/PKI or a separate sensor
  credential lifecycle for the one-sensor pilot.

Value: one client bundle owns the whole local flow.

Cost/risk: the managed-browser policy, exact-origin CORS and preflight behavior
become deployment/firmware contracts. The 10-second hold creates at most one
lightweight request per active client instead of frequent polling.

### 2. Selected proposal detector

- Use MediaPipe BlazeFace Full-range as the only implemented pilot detector.
- Use the ready MediaPipe browser runtime without TensorFlow.js or a separate
  project-selected ML runtime.
- Identify the detector with `detector_id`, model version and client release.
- Ship the model file as a separate versioned release asset rather than
  embedding it in JavaScript.
- Update the model only with a normal `SpaPromoClient` release/reload. No model
  OTA service, dynamic channel, rollback state machine or hot swap is
  introduced.
- Keep YuNet 2026may FP32 as a documented fallback decision only. Do not ship,
  integrate or abstract over it while BlazeFace remains technically viable.
- If model validation or load fails, remain in advertising and show a
  recoverable operator-visible client error; do not start an attempt.

Value: the browser-ready detector supports the required multi-face proposal
role with less project-owned preprocessing/postprocessing and without taking
search authority from the server.

Cost/risk: one browser detector and versioned model asset. A concrete
incompatibility reopens the fallback decision; it does not authorize two
implementations.

### 3. Selected crop contract

- For each detector bbox, create one centered square region with total side
  length `1.2 × max(bbox_width, bbox_height)`.
- Clip the region to the source frame without inventing pixels.
- Preserve source orientation as displayed by the video pipeline.
- Do not align, normalize landmarks or upscale a small crop.
- Downscale proportionally only when the crop's longest side exceeds `512 px`.
- Encode as ordinary sRGB JPEG without EXIF or other source metadata.
- Expose `jpeg_quality` on the client configuration/debug page as a dropdown
  with exactly `0.7`, `0.75`, `0.8`, `0.85`, `0.9` and `0.95`; arbitrary numeric
  input is not needed.
- Use `0.85` as the default JPEG quality.
- Persist the selected JPEG quality in the kiosk browser profile through
  ordinary `localStorage` and apply changes starting with the next Attempt. No
  server-side setting or separate lifecycle is introduced.
- Include original frame dimensions, bbox, crop rectangle, crop dimensions and
  detector confidence in the manifest. Also record the selected JPEG quality so
  an admitted Attempt remains diagnostically reproducible.

Value: enough context for native server redetection with bounded bytes.

Cost/risk: a wider crop can contain another face near a group boundary, but the
server already validates/ranks proposals. This is cheaper than client
pipeline-specific alignment.

### 4. Selected request shape

- Use one synchronous `multipart/form-data` request.
- Part `manifest` is versioned JSON.
- Every proposal has one request-local ordinal `occurrence_index` and references
  exactly one JPEG part.
- The manifest contains:
  - `schema_version: 1`, client-generated UUID `attempt_id` and
    `trigger_source`;
  - `client_release`, `detector_id`, `model_version` and `jpeg_quality`;
  - selected browser `camera_device_id`;
  - `reference_series_ready_at` as a client wall-clock correlation marker;
  - `local_detection_completed_ms` and `request_started_ms` as monotonic offsets
    from `reference_series_ready_at = 0`;
  - for each occurrence: ordinal index, frame index/offset, detector confidence
    and crop part name.
- Keep `spa_client_token` in the Authorization header, never in the manifest.
- Derive `spa_id` on the server from `spa_client_token`; do not accept a
  client-supplied `spa_id` in the manifest.
- Reuse the same endpoint for a zero-proposal metadata-only request.
- A compliant client stops at occurrence 20 and downscales crops above the
  accepted side limit. The server rejects a total request body larger than
  `20 MiB` with HTTP `413` before domain admission; the client does not create a
  metadata-only oversize-reporting path or a separate domain failure.
- Retain the existing standard HTTP statuses and typed domain-result response;
  do not add a custom error framework in FT-003.

Value: one inspectable request, no base64 overhead and complete correlation.

Cost/risk: multipart parsing and per-part validation, both inside the already
accepted application boundary.

### 5. Selected structural pilot caps

- Maximum occurrence parts: `20`.
- Maximum encoded crop side: `512 px`.
- No separate maximum complete multipart body.
- Bound input camera frame dimensions through deployment configuration before
  ring-buffer/detector work. Exact dimensions remain a camera/site setting, not
  an FT-003 design gate.

These are protective pilot caps, not quality thresholds or performance claims.
The occurrence cap is enforced during local detection: after the twentieth
occurrence, the client stops processing remaining frames and prepares the
request. The crop-size cap bounds decoded input to at most `20 × 512 × 512`
pixels. The fixed manifest shape and multipart part count bound the normal
client request. A separate server-side transport guard rejects a total request
body larger than `20 MiB` with HTTP `413` before domain admission.

Value: bounds local detector work, memory and decode cost at the surfaces that
actually create them.

Cost/risk: the encoded request size varies with scene complexity and selected
JPEG quality, but it remains bounded by 20 crops of at most `512 px`.

Separate aggregate-pixel, per-JPEG-byte and manifest-size caps are not
introduced. The only encoded-size guard is the `20 MiB` total request-body
transport limit.

## Selected Directions

Explicitly selected by the operator in this session and amended by the
operator on 2026-07-29:

- A representative benchmark is not required to select the FT-003 client
  route, detector/runtime/model/update, crop, schema or hard bounds.
- These choices should be discussed and selected now rather than left as one
  benchmark-dependent feature blocker.
- The single pilot route is browser-native Chromium; no local hardware/ML bridge
  is built.
- `SpaPromoClient` loads from the central HTTPS origin; no local web server is
  used.
- ESP32 publishes a fixed `.local` name through mDNS, for example
  `fm-sensor1.local`.
- Chromium receives trigger events through HTTP long-poll with a 10-second
  timeout, not WebSocket.
- The controlled kiosk pre-authorizes the central origin for Local Network
  Access through `LocalNetworkAccessAllowedForUrls`.
- ESP32 allows exactly the Face Moment HTTPS origin through CORS and processes
  OPTIONS preflight when Authorization is present.
- One manually provisioned sensor `Bearer` secret is stored in the managed kiosk
  browser profile and validated by ESP32. It is absent from URLs and logs.
- No pairing, automatic secret rotation, PKI or separate sensor credential
  lifecycle is introduced.
- The primary local proposal detector is MediaPipe BlazeFace Full-range using
  its browser runtime.
- The BlazeFace model is a separate versioned asset delivered with the
  `SpaPromoClient` release, not embedded in JavaScript.
- TensorFlow.js and a separate project-selected ML runtime are not introduced.
- YuNet 2026may FP32 is a fallback only if BlazeFace proves technically
  unusable. Both detectors are never implemented simultaneously.
- A representative benchmark is not a gate for this detector selection.
- Each proposal crop is a centered square with side
  `1.2 × max(bbox_width, bbox_height)`, clipped to the source frame without
  alignment or upscaling.
- Proposal crops use ordinary sRGB JPEG without EXIF or source metadata.
- The `SpaPromoClient` configuration/debug page exposes JPEG quality through one
  dropdown with values `0.7`, `0.75`, `0.8`, `0.85`, `0.9` and `0.95`.
- The default JPEG quality is `0.85`.
- The selected quality is persisted in kiosk-profile `localStorage` and applies
  from the next Attempt; it is not a server-side setting.
- One ready reference series produces one synchronous `multipart/form-data`
  request containing a JSON `manifest` and one JPEG part per occurrence.
- A zero-occurrence request uses the same endpoint and sends only the manifest.
- The manifest identity block contains only `schema_version: 1`, UUID
  `attempt_id`, `trigger_source`, `client_release`, `detector_id`,
  `model_version` and `jpeg_quality`.
- `spa_id` and secrets are absent from the manifest. The server derives СПА from
  `spa_client_token` supplied through the Authorization header.
- The timing block contains `reference_series_ready_at` for correlation plus
  `local_detection_completed_ms` and `request_started_ms` measured on one client
  monotonic clock from ready-series zero. Client/server wall clocks are never
  subtracted.
- Each occurrence uses a request-local ordinal `occurrence_index` plus
  `frame_index`, `frame_offset_ms`, `detector_confidence` and `crop_part`.
- No occurrence UUID, `bbox_px`, `crop_rect_px`, `source_frame_width_px` or
  `source_frame_height_px` is sent.
- The manifest includes the selected browser `camera_device_id`, without a
  camera label or separate configuration snapshot.
- Local proposal detection stops as soon as the twentieth occurrence is found.
  The request contains at most those first 20 occurrences; the client does not
  continue detecting faces in the remaining frames.
- The first-20 cap is traversal order only, not quality ranking, tracking,
  clustering or person deduplication.
- Frames are traversed chronologically from the earliest pre-trigger frame to
  the latest post-trigger frame. Within one frame, the client preserves the
  occurrence order returned by BlazeFace.
- Crops whose longest side exceeds `512 px` are proportionally downscaled to
  `512 px`; smaller crops are never upscaled.
- The server rejects a multipart request body larger than `20 MiB` with HTTP
  `413` before domain admission. This is a transport failure, not a domain
  oversize outcome, and the client does not rank or truncate crops to fit it.
- Camera frames above the deployment-configured maximum are downscaled before
  entering the ring buffer/detector path. The exact maximum is selected with the
  camera/site configuration and does not block feature design.

## Rejected Directions

Explicitly rejected or already excluded by accepted project direction:

- representative benchmark as a prerequisite for FT-003 design/tasking;
- local face ranking, top-five selection, authoritative quality gating,
  tracking, clustering or person deduplication;
- sending an arbitrary crop subset when the complete set exceeds bounds;
- client-side embeddings/search;
- mandatory full/downscaled reference-frame upload;
- building browser and bridge routes together or creating a generic
  device/runtime plugin framework.
- WebSocket as the ESP32-to-client transport.
- a local web server for `SpaPromoClient`.
- parallel BlazeFace and YuNet implementations or a generic detector/runtime
  abstraction.

## Assumptions

- The current default capture series is approximately nine frames; the caps are
  intended to tolerate several face occurrences per frame without promising
  unbounded group density.
- A release-pinned BlazeFace model is small enough for ordinary versioned asset
  delivery; no model-management subsystem is needed.
- Exact structural caps are reversible pilot contract values, but changing them
  later must remain a deliberate client/server compatibility change.

## Open Questions

No material FT-003 design question remains in this brainstorm.

The exact camera input dimensions remain a deployment/site configuration
choice, alongside the exact camera hardware; they are not a representative
benchmark or feature-tasking gate.
