# EP-003 — Explainable Diagnostics and Calibration

## Value

The operator can understand outcome and latency without sensitive access, while
an authorized developer can inspect available correlated evidence and explicit
gaps, record ground truth and derive explainable recommendations without
automatic serving changes.

## Features

- [FT-007](../features/FT-007.md): Core Attempt and best-effort protected
  diagnostic evidence.
- [FT-008](../features/FT-008.md): Role-scoped Attempts investigation.
- [FT-009](../features/FT-009.md): Developer structured Log Explorer.
- [FT-010](../features/FT-010.md): Person/detection ground-truth annotation.
- [FT-011](../features/FT-011.md): Explainable threshold and input-quality
  Calibration.

## Success Metrics

- Every accepted controlled attempt, including failures, has a core correlation
  identity and stage timeline; missing detailed evidence is visible as
  `incomplete`.
- An operator sees only sanitized outcome/timing evidence; an authorized
  developer can trace available versions, parameters, decisions, artifacts and
  logs, while missing detail remains `incomplete`.
- Calibration exposes all required threshold profiles, one-dimensional quality
  recommendations and contributing-attempt evidence without changing serving
  settings automatically.

## Acceptance Criteria

- Browser/server events, available decision records and protected artifacts are
  navigable through one core Attempt correlation context.
- Logging is non-blocking and contains none of the forbidden payload classes.
- Annotation semantics support correct, false and missed calculations at
  person/detection level.
- Technical logs, ordinary attempt/evidence data and promoted Calibration subsets
  follow their distinct retention and privacy rules.
- A Calibration run may delay the shared background worker; restart marks it
  interrupted/failed, resumes photo work and leaves rerun manual.
- Operator, photographer and developer access remains separated according to
  the PRD authorization contract.
