# Face Moment: поступление фотографий

Обновлено: 2026-07-11

## 0. Статус документа

Этот документ фиксирует концепцию поступления коммерческих фотографий в Face
Moment через два канала:

1. прямую HTTPS-загрузку в приложение;
2. публичную ссылку на папку в Яндекс Диске из произвольного аккаунта
   фотографа.

Документ уточняет `batch upload` из `IDEA_APP.md`. Хранение originals,
background processing, face-recognition pipelines и поиск остаются в
`IDEA_APP.md`; серверная топология и MinIO — в `IDEA_OS.md`.

Используются четыре статуса:

- **Требование** — поведение, которое система обязана обеспечивать.
- **Принятое архитектурное решение** — текущий способ реализации, выбранный
  осознанно.
- **Рекомендация** — предпочтительная стартовая реализация, которую можно
  заменить без изменения требований и принятых границ.
- **Кандидат на будущее** — возможное усложнение, которое нельзя добавлять без
  подтверждённой необходимости.

## 1. Главный принцип

**Принятое архитектурное решение:** Face Moment не угадывает SPA и рабочую дату
по имени файла, EXIF, времени загрузки или свободно заданному имени папки.

Сначала создаётся или регистрируется immutable batch:

~~~text
batch_id
+ spa_id
+ visit_date
+ timezone
+ source_type
~~~

После этого к batch привязывается зафиксированный набор файлов.

~~~text
прямая HTTPS-загрузка ─┐
                      ├→ sealed ingest batch → MinIO → photos → processing jobs
публичная Yandex-ссылка┘
~~~

**Почему принято:** часы камеры могут быть сбиты, EXIF может отсутствовать,
названия файлов повторяются, а время создания ресурса в Яндекс Диске отражает
загрузку в облако, а не съёмку. Только явно подтверждённый batch однозначно
задаёт бизнес-контекст.

---

## 2. Термины

### 2.1 `visit_date`

Бизнес-дата, внутри которой фотографии участвуют в поиске. Она задаётся явно в
timezone соответствующего SPA.

`visit_date` не вычисляется автоматически из upload time или EXIF.

### 2.2 `captured_at`

Фактическое время съёмки, извлечённое из EXIF и нормализованное в UTC. Оно
используется для сортировки и проверки batch, но не является единственным
источником `visit_date`.

### 2.3 `sealed batch`

Batch, для которого пользователь подтвердил SPA, `visit_date` и полный набор
файлов. После `sealed` нельзя добавлять или заменять файлы. Опоздавшие файлы
оформляются отдельным supplement batch.

### 2.4 `source snapshot`

Неизменяемый список ресурсов источника на момент подтверждения batch. Для
Яндекс Диска snapshot содержит как минимум:

~~~text
resource_id
path
size
source sha256
mime_type
EXIF date_time: nullable
~~~

---

## 3. Инварианты ingest

1. Каждый импортируемый файл принадлежит ровно одному `batch_id`.
2. `spa_id`, `visit_date` и `timezone` принадлежат batch, а не отдельному файлу.
3. После `sealed` состав batch и его привязка неизменяемы.
4. EXIF может подтвердить или опровергнуть ожидания, но не может молча изменить
   `spa_id` или `visit_date`.
5. Имя файла не является идентификатором фотографии.
6. Имя папки является подсказкой и cross-check, но не source of truth.
7. Файл не создаёт processing job, пока не сохранён и не проверен в MinIO.
8. Повторный import того же source resource и checksum идемпотентен.
9. Расхождение metadata переводится в `needs_review`; система не выбирает
   «наиболее вероятную» привязку.
10. Незарегистрированная публичная ссылка или незапечатанный batch не
    обрабатываются.

## 4. Каналы поступления

### 4.1 Прямая HTTPS-загрузка

**Принятое архитектурное решение:** прямая загрузка выполняется через uploader
Face Moment. Фотографу не выдаются SSH, SFTP, SMB или MinIO credentials.

~~~text
авторизация
→ выбор разрешённого SPA и visit_date
→ создание batch_id
→ загрузка файлов по HTTPS с retry
→ server-side SHA-256 и validation
→ сводка
→ «Закрыть batch»
→ sealed
~~~

Backend потоково записывает original во внутренний MinIO и не держит весь файл
в RAM. Этот канал является предпочтительным, потому что даёт минимальный
`ingest_to_searchable` и не зависит от сторонней публичной ссылки.

### 4.2 Публичная ссылка Яндекс Диска

**Принятое архитектурное решение:** фотографы могут использовать любые личные
или рабочие аккаунты Яндекс Диска. Face Moment не получает OAuth-доступ к этим
аккаунтам.

Яндекс Диск используется как транспорт:

~~~text
фотограф загрузил отдельную папку
→ дождался завершения синхронизации
→ включил публичную ссылку с разрешённым скачиванием
→ передал ссылку через структурированный intake
→ Face Moment проинспектировал папку
→ человек подтвердил SPA, дату и состав
→ Face Moment скопировал originals в MinIO
~~~

После успешного копирования MinIO становится source of truth. Доступность
публичной ссылки больше не влияет на обработку или выдачу фотографии.

## 5. Действия фотографа для Яндекс Диска

### 5.1 Минимальная инструкция

1. Создать отдельную папку для одного SPA и одного рабочего дня.
2. Положить в неё готовые к продаже JPEG без вложенных каталогов.
3. Дождаться полного завершения синхронизации Яндекс Диска.
4. Создать публичную ссылку и не запрещать скачивание.
5. Передать ссылку в Face Moment.
6. Выбрать SPA и рабочую дату.
7. Проверить найденное количество файлов и EXIF-сводку.
8. Нажать `Подтвердить batch`.

Нажатие `Подтвердить batch` является `READY`-сигналом. Отдельный marker-файл
фотографу создавать не требуется.

### 5.2 Структурированный intake

**Требование:** публичная ссылка передаётся не свободным текстом в неизвестном
контексте, а через канал, который фиксирует:

~~~text
public_url
spa_id
visit_date
submitter identity
ready confirmation
~~~

**Рекомендация для MVP:** короткая web-форма в Face Moment. Авторизованный
администратор или фотограф вставляет ссылку, выбирает SPA и дату, после чего
получает inspection preview.

**Кандидат на будущее:** Telegram-бот как UI adapter к тому же backend API.

Пример ответа intake:

~~~text
Найдена папка «Да 0709»

Файлов: 453
EXIF:
- 08.07.2026 — 438
- 09.07.2026 — 14
- без даты — 1

SPA: [выбрать]
Рабочая дата: [выбрать]

[Подтвердить]
[Изменить дату]
[Разделить]
[Отменить]
~~~

### 5.3 Naming convention

**Рекомендация:** для человеческой навигации фотограф именует папку строго:

~~~text
FM__<SPA_CODE>__<YYYY-MM-DD>__<BATCH_NO>
~~~

Пример:

~~~text
FM__DA__2026-07-08__01
~~~

Правила:

- `SPA_CODE` выбирается из фиксированного справочника;
- дата записывается только в ISO-формате `YYYY-MM-DD`;
- `BATCH_NO` различает несколько передач за один день;
- parser использует full-match, без fuzzy matching;
- несовпадение имени с intake metadata создаёт warning или `needs_review`.

Naming convention не заменяет структурированную передачу ссылки.

### 5.4 Временный fallback без web-формы

Пока intake UI не готов, допускается строгое сообщение:

~~~text
SPA: DA
Дата: 2026-07-08
Ссылка: https://disk.yandex.ru/d/...
Загрузка завершена: да
~~~

Оператор переносит эти значения в админку и подтверждает inspection preview.

## 6. Интеграция с публичным API Яндекс Диска

### 6.1 Получение содержимого

Для публичного ресурса используется endpoint:

~~~text
GET https://cloud-api.yandex.net/v1/disk/public/resources
~~~

Основные параметры:

~~~text
public_key=<public URL>
path=/
limit=<page size>
offset=<page offset>
fields=<required response fields>
~~~

Importer читает все страницы `_embedded.items`, а не только первую страницу.
Корневой ресурс обязан иметь `type = dir`.

### 6.2 Inspection

До подтверждения batch приложение получает:

- folder name;
- root `resource_id`;
- общее количество ресурсов;
- количество JPEG, RAW и прочих типов;
- общий размер;
- распределение EXIF по календарным датам;
- количество файлов без EXIF;
- повторяющиеся имена;
- доступные source checksums.

Inspection ничего не импортирует и не создаёт photo-processing jobs.

### 6.3 Sealing и snapshot

После подтверждения система сохраняет полный snapshot. Рекомендуемый
`snapshot_sha256` вычисляется по отсортированному набору:

~~~text
(resource_id, path, size, source_sha256)
~~~

Snapshot определяет точный набор файлов batch. Файлы, появившиеся после
подтверждения, не подхватываются автоматически.

Если повторная проверка перед download показывает замену или исчезновение
ресурса, batch переходит в `needs_review`.

### 6.4 Скачивание

Для каждого зафиксированного файла запрашивается download URL:

~~~text
GET https://cloud-api.yandex.net/v1/disk/public/resources/download
~~~

Параметры:

~~~text
public_key=<public URL>
path=<path from snapshot>
~~~

Полученный `href` используется немедленно. Файл потоково переносится в MinIO,
при этом Face Moment самостоятельно считает SHA-256 и сравнивает размер.

Object key строится из UUID или deterministic ingest identity, а не из
оригинального имени файла.

### 6.5 Ошибки публичной ссылки

Batch не может быть подтверждён или импортирован, если:

- ссылка отозвана или истекла;
- ссылка защищена неизвестным паролем;
- владелец запретил скачивание;
- resource является файлом, а не папкой;
- папка изменилась после sealing;
- API вернул неполный список или download завершился не полностью.

Transient ошибки и rate limit повторяются с bounded retry и backoff. При
исчерпании retry сохраняется per-file error, а batch остаётся resumable.

## 7. Определение рабочей даты

### 7.1 Источники даты

| Источник | Роль | Может задать `visit_date` |
|---|---|---|
| Выбор в intake | Бизнес-решение | Да |
| EXIF `date_time` | Проверка и `captured_at` | Нет, без подтверждения |
| Имя папки | Cross-check | Нет |
| Yandex `created/modified` | Время облачного ресурса | Нет |
| Имя файла | Идентификация камеры | Нет |

### 7.2 Правила проверки

| Ситуация | Поведение |
|---|---|
| Все EXIF относятся к выбранной дате | Разрешить подтверждение. |
| Все EXIF относятся к другой дате | Показать конфликт, потребовать явное исправление или override. |
| В папке несколько EXIF-дат | `needs_review`: выбрать одну business date или разделить на batches. |
| Часть файлов без EXIF | Показать количество; разрешить явное подтверждение batch date. |
| Все файлы без EXIF | Только ручной выбор и подтверждение даты. |
| Съёмка пересекает полночь | Применить заранее принятое правило business day и capture window. |

Система никогда не выполняет automatic rebind файла на другой SPA или день.

### 7.3 Съёмка после полуночи

До production необходимо выбрать одно правило:

1. `visit_date` равна локальной календарной дате каждого кадра; или
2. `visit_date` равна дате начала рабочей смены, а capture window может перейти
   через полночь.

**Рекомендация:** использовать дату начала смены, если фактический workflow SPA
регулярно продолжается после полуночи. Иначе использовать календарную дату SPA.

## 8. Проверка файлов

### 8.1 MVP-форматы

**Рекомендация:** processing принимает готовые к продаже JPEG.

RAW (`CR2`, `CR3`, `NEF`, `ARW`), sidecar-файлы и вложенные каталоги не
импортируются автоматически. Они показываются в inspection и требуют удаления
или отдельного будущего workflow.

### 8.2 Server-side validation

Для каждого файла проверяются:

- `type = file`;
- MIME и magic bytes;
- допустимый размер;
- полное декодирование изображения;
- width/height;
- EXIF orientation;
- source size и checksum;
- самостоятельно рассчитанный SHA-256 после download.

Файл с ошибкой не создаёт `photos` и processing job.

## 10. Lifecycle

~~~text
draft
→ inspecting
→ awaiting_confirmation
→ sealed
→ importing
→ imported
→ processing
→ completed
~~~

Боковые состояния:

~~~text
needs_review
failed
cancelled
~~~

- `sealed` означает неизменяемый file snapshot.
- `imported` означает, что все принятые originals находятся в MinIO.
- `processing` означает, что background face-processing продолжается.
- `completed` означает terminal processing state для всех принятых файлов.

UI не должен называть batch готовым, если импортировано `451/453` файлов.

---

## 11. Идемпотентность и восстановление

1. Повтор inspection одной ссылки обновляет только draft summary.
2. Повторное подтверждение того же snapshot является no-op.
3. Повторный download того же `resource_id + source_sha256` публикует тот же
   итоговый file record.
4. Если MinIO object записан, но DB transaction не завершилась, retry использует
   тот же deterministic staging key.
5. Совпадение checksum внутри того же batch считается duplicate.
6. Совпадение checksum с другим SPA или датой создаёт `binding_conflict` и не
   вызывает automatic rebind.
7. Истёкший download URL запрашивается заново; он не сохраняется как durable
   metadata.

## 13. MVP ingest

1. Создание direct batch в админке.
2. Прямая потоковая HTTPS-загрузка JPEG в MinIO.
3. Intake-форма для публичной Yandex-ссылки.
4. Inspection публичной папки с pagination.
5. Выбор SPA и `visit_date` человеком.
6. EXIF histogram и список неподдерживаемых типов.
7. Human confirmation как seal operation.
8. Immutable source snapshot.
9. Per-file resumable download в MinIO.
10. Server-side SHA-256, decode validation и duplicate detection.
11. Единое создание `photos`, `photo_pipeline_states` и jobs для обоих каналов.
12. Статусы batch и понятная сводка ошибок.

### 13.1 Не является MVP gate

- Telegram-бот;
- автоматическое разбиение mixed-date folder;
- OAuth-доступ к аккаунтам фотографов;
- общий корпоративный аккаунт Яндекс Диска;
- обработка RAW;
- watcher произвольных папок;
- автоматическое доверие naming convention;
- импорт новых файлов, добавленных после sealing.

## 14. Финальная формула

~~~text
SPA и visit_date задаются batch-ом
+
прямая загрузка и публичная Yandex-ссылка сходятся в один ingest pipeline
+
публичная ссылка может принадлежать любому аккаунту
+
структурированный intake фиксирует link + SPA + date + ready confirmation
+
API inspection показывает count, types и EXIF histogram до импорта
+
human confirmation создаёт immutable snapshot
+
каждый файл идемпотентно копируется в MinIO и проверяется сервером
+
только после этого создаются photos и processing jobs
+
имя папки и EXIF являются cross-check, а не source of truth
~~~

Главный принцип:

> Не угадывать контекст фотографии. Сначала зафиксировать batch, затем
> импортировать его точный состав.
