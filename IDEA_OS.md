# Face Moment: сервер, ОС и display/kiosk


Обновлено: 2026-07-10

## 0. Статус документа

Этот документ фиксирует продуктовую концепцию, принятые архитектурные решения и границы MVP.

Используются три статуса:

- **Требование** — поведение, которое система обязана обеспечивать.
- **Принятое архитектурное решение** — текущий способ реализации, выбранный осознанно.
- **Кандидат на будущее** — возможное усложнение, которое нельзя добавлять без измеримой необходимости.

### Правило для разработчиков и AI-агентов

Принятые решения нельзя заменять на Redis, Celery, RQ, Kafka, ANN-индексы, автоматическую кластеризацию, распределённый scheduler или другие более сложные механизмы только потому, что они считаются типичными для подобных систем.

Архитектуру разрешено усложнять только если одновременно выполнены два условия:

1. Текущая реализация не выполняет зафиксированный SLA или создаёт подтверждённую проблему.
2. Проблема подтверждена метриками, benchmark-ом или эксплуатационными данными.

**Почему принято:** проект следует KISS. Сложность добавляется для решения уже наблюдаемой проблемы, а не для гипотетического будущего масштаба.

## 1. Пользовательские сценарии display/kiosk

### 2.2 Промо-экран на выходе

1. Камера делает 3–5 кадров.
2. Система выбирает лучший кадр по размеру лица, резкости, освещению и pose.
3. Для MVP обрабатывается одно доминирующее лицо.
4. Кадр отправляется на центральный `RealtimeFaceService`.
5. Сервис создаёт embedding и выполняет точный поиск.
6. При достаточной уверенности создаётся короткоживущая promo-session.
7. Экран показывает несколько preview и QR-код.
8. Покупка и скачивание происходят на телефоне.

Если в кадре несколько сопоставимых по качеству лиц и нельзя надёжно выбрать одно доминирующее лицо, экран не должен показывать персональные preview.

**Почему принято:** выбор одного доминирующего лица сохраняет предсказуемый UX и не требует трекинга нескольких людей и нескольких параллельных экранных сессий в MVP.

### 2.3 Display mode вместо kiosk mode

Промо-экран выполняет только:

- захват кадров;
- показ рекламы между поисковыми событиями;
- показ найденных preview;
- показ QR-кода;
- автоматическое восстановление соединения после сетевого сбоя.

На экране нет сенсорной навигации, оплаты и скачивания.

**Почему принято:** телефон клиента уже предоставляет безопасный и привычный интерфейс для выбора, оплаты и скачивания. Полноценный kiosk mode не даёт достаточной пользы для своей сложности.

### 2.4 Display-приложение

Промо-интерфейс реализуется как web-приложение, открытое в Chromium на весь экран.

Поведение:

~~~text
обычный режим
→ показ рекламных слайдов или видео
→ получено событие с результатом поиска
→ показ preview и QR-кода
→ истёк TTL результата
→ возврат к рекламе
~~~

События от backend передаются через Server-Sent Events. При потере сети display-приложение продолжает показывать локально закэшированную рекламу и автоматически переподключается.

**Почему принято:** web-приложение проще обновлять централизованно, чем отдельное desktop-приложение. SSE достаточно для односторонней доставки событий от backend к экрану и проще WebSocket.

## 2. Принятая топология сервера

### 3.1 Один центральный сервер

Все 10–15 SPA используют один сервер в РФ.

На сервере работают:

- backend API и админка;
- PostgreSQL + pgvector;
- объектное хранилище;
- один `BackgroundPhotoWorker`;
- один `RealtimeFaceService`;
- SFace и Buffalo M;
- сервис выдачи preview и оригиналов;
- KDE Plasma и один локальный display-клиент на подключённом HDMI-мониторе.

Центральный сервер по HDMI может обслуживать только один физически подключённый экран. В остальных SPA используются отдельные промо-клиенты с камерой и экраном, подключающиеся к центральному backend.

**Почему принято:** централизованная схема упрощает развёртывание, обновление моделей, мониторинг, резервное копирование и поддержку 10–15 объектов. Текущий объём не требует отдельного inference-сервера в каждом SPA.

## 3. CPU reservation и процессы

### 8.3 CPU reservation

Стартовая конфигурация:

- процессор класса Intel Core i5-13400 с 10 физическими ядрами;
- 2 физических P-core и оба их Hyper-Thread закреплены только за `RealtimeFaceService`;
- остальные P-core и E-core доступны `BackgroundPhotoWorker`;
- закрепление выполняется через Linux cpuset / Docker Compose `cpuset`;
- internal thread pools OpenCV, ONNX Runtime, OpenVINO, OpenMP и BLAS ограничиваются числом разрешённых logical CPU.

CPU-набор задаётся deployment-конфигурацией и может быть изменён с перезапуском процессов без изменения кода.

**Почему принято:** постоянное разделение CPU даёт предсказуемую realtime latency без остановки background worker, priority scheduler, Redis-флагов и кооперативной паузы.

### 8.4 Никакой приоритизации и остановки процессов

В системе отсутствуют:

- `reference_mode`;
- pause/resume фонового worker-а;
- priority jobs;
- hard preemption;
- `ResourceManager`;
- Redis-флаги управления CPU.

Background worker продолжает работу во время reference-запроса, но не имеет доступа к двум зарезервированным P-core.

**Почему принято:** CPU isolation решает ту же задачу статически и значительно проще. Динамическая приоритизация добавляла race conditions, зависшие паузы и сложное восстановление jobs.

### 8.6 Условие масштабирования realtime

Дополнительные P-core или второй экземпляр RealtimeFaceService разрешены, если:

- `realtime_queue_wait_p95` устойчиво превышает 2 секунды;
- `trigger_to_preview_p95` устойчиво превышает 5 секунд при нормальной сети;
- сервис регулярно отклоняет запросы из-за заполнения in-memory queue.

Следующий шаг:

~~~text
добавить ещё 2 P-core
+
запустить второй экземпляр RealtimeFaceService
+
распределять запросы обычным backend/load balancer
~~~

**Почему принято:** центральный сервер обслуживает 10–15 SPA, поэтому одновременные запросы возможны. Масштабирование должно происходить по измеренной очереди ожидания, а не заранее.

## 11. Хранилище

### 11.1 Расчёт центрального объёма

~~~text
45 000–90 000 фото в месяц
~~~

Оценка только для originals:

| Средний размер | 45 000 фото | 90 000 фото |
|---:|---:|---:|
| 5 MB | 225 GB | 450 GB |
| 10 MB | 450 GB | 900 GB |
| 15 MB | 675 GB | 1.35 TB |
| 25 MB | 1.125 TB | 2.25 TB |

Дополнительно нужны preview, thumbnails, БД, временные файлы, логи и свободное место для безопасной работы.

2 TB больше не считается гарантированно достаточным объёмом для 10–15 SPA. Стартовый ориентир — не менее 4 TB usable primary storage с уточнением после измерения реального среднего размера фотографии.

**Почему принято:** прежняя оценка 2 TB относилась к одному SPA. Центральный сервер увеличивает месячный объём до 15 раз.

### 11.2 Object storage

Originals, previews и thumbnails хранятся в MinIO или совместимом S3 object storage на центральном сервере.

PostgreSQL хранит только object keys и метаданные.

**Почему принято:** object storage упрощает атомарную загрузку, lifecycle, выдачу короткоживущих signed URLs и возможный перенос файлов на отдельное хранилище без изменения бизнес-логики.

### 11.3 Резервная копия

Backup originals и PostgreSQL должен находиться на другом физическом носителе или сервере. MinIO на одном диске не является резервной копией.

**Почему принято:** центральный сервер является единой точкой хранения для 10–15 SPA; отказ одного NVMe не должен уничтожить все коммерческие оригиналы.

## 12. Серверная ОС и базовая конфигурация

### 12.1 Kubuntu LTS

Серверная ОС — Kubuntu 26.04 LTS с KDE Plasma.

KDE используется для:

- графической установки и первоначальной настройки неподготовленным человеком;
- проверки сети, HDMI, звука, камеры и браузера;
- организации первого удалённого доступа;
- работы локального display-клиента на HDMI-мониторе.

Дополнительное потребление KDE порядка нескольких гигабайт RAM допустимо для сервера с 64 GB RAM.

**Почему принято:** сервер физически разворачивает неподготовленный пользователь, а монитор является частью продукта. Kubuntu уменьшает риск ошибок первоначальной установки и одновременно предоставляет готовую графическую среду для display-приложения.

### 12.2 Один системный пользователь

Используется один обычный пользователь системы:

- автоматический вход в KDE;
- sudo;
- SSH и удалённый доступ;
- управление Docker;
- запуск Chromium/display-приложения.

Отдельные пользователи `admin` и `display` не создаются.

**Почему принято:** для текущих физических условий и уровня риска разделение пользователей создаёт лишние инструкции и точки отказа при удалённой поддержке, не давая достаточной практической пользы.

### 12.3 Независимый запуск Docker

Устанавливается Docker Engine, а не Docker Desktop.

`docker.service` и `containerd.service` запускаются systemd при загрузке ОС до входа пользователя в KDE. Все постоянные контейнеры имеют Compose policy:

~~~yaml
restart: unless-stopped
~~~

После первоначального `docker compose up -d` backend, PostgreSQL, MinIO, `BackgroundPhotoWorker` и `RealtimeFaceService` запускаются независимо от графической сессии.

Падение или перезапуск KDE/Chromium не должен останавливать серверные контейнеры.

**Почему принято:** графическая сессия нужна только для локального экрана и обслуживания. Backend должен начать работу сразу после загрузки ОС и продолжать работу независимо от состояния GUI.

### 12.4 Автоматический display-сеанс

Настраиваются:

- автоматический вход единственного пользователя через SDDM;
- user-level systemd service для запуска Chromium;
- Chromium на весь экран с display URL данного SPA;
- `Restart=always` и короткая задержка перезапуска браузера;
- отключение первого запуска, crash bubble и лишних диалогов браузера;
- отключение сна, suspend, блокировки экрана и гашения HDMI;
- автоматическое восстановление display-страницы после сетевой ошибки.

Так как Kubuntu 26.04 использует Wayland, управление гашением экрана выполняется через Plasma Power Management и системные sleep targets, а не через устаревший `xset`.

**Почему принято:** Chromium может упасть или потерять соединение, но экран должен восстанавливаться без участия локального пользователя.

### 12.5 CPU и графическая среда

KDE и Chromium не изменяют принятую схему CPU reservation:

- `RealtimeFaceService` закрепляется за двумя физическими P-core через Docker `cpuset`;
- `BackgroundPhotoWorker` не имеет доступа к этим P-core;
- Chromium через user-level systemd service закрепляется за background CPU с помощью `CPUAffinity`;
- остальная малонагруженная KDE-сессия сначала отдельно не ограничивается.

**Почему принято:** основную конкуренцию создают inference и воспроизведение рекламы в Chromium. Их явного разделения достаточно; полная изоляция всей KDE-сессии через отдельные cgroup partitions для MVP избыточна.

### 12.6 Hardware

Пилотная отправная точка:

~~~text
Intel Core i5-13400 или CPU не слабее
64 GB RAM рекомендуется для центрального сервера
не менее 4 TB usable NVMe для primary storage
отдельное backup storage
Kubuntu 26.04 LTS
PostgreSQL + pgvector
MinIO
ONNX Runtime / OpenVINO / OpenCV / InsightFace
без GPU на старте
~~~

32 GB RAM допустимы для раннего прототипа, но не фиксируются как целевая production-конфигурация на 10–15 SPA.

**Почему принято:** CPU-only сервер достаточен для проверки текущего объёма, а окончательный размер CPU/RAM определяется по `ingest_to_searchable` и realtime percentiles. GPU не добавляется до подтверждения CPU bottleneck-а.

## 15. Что входит в MVP сервера и display

1. Один центральный сервер для пилотных SPA.
4. MinIO/S3-compatible storage.
19. CPU reservation через cpuset.
21. Kubuntu 26.04 LTS с автоматическим входом одного пользователя.
22. Автозапуск Chromium и показ рекламы между результатами.
23. Независимый от KDE автозапуск Docker-контейнеров.

## 16. Что осознанно не входит в MVP сервера и display

- Redis;
- Celery, RQ, Arq и другие queue frameworks;
- несколько priority queues;
- pause/resume background processing;
- `reference_mode` и `ResourceManager`;
- динамическая приоритизация CPU;
- distributed scheduler;
- Kubernetes;
- отдельный inference-сервер в каждом SPA;
- GPU-инфраструктура;
- полноценный kiosk mode;
- оплата и скачивание на промо-экране.

**Почему принято:** ни один из этих механизмов пока не решает подтверждённый bottleneck. Их добавление увеличит стоимость разработки, тестирования и эксплуатации.

## 17. Условия пересмотра архитектуры сервера и display

| Текущее решение | Когда разрешено пересмотреть | Следующий минимальный шаг |
|---|---|---|
| Один realtime instance, 2 P-core | queue wait p95 > 2 s или trigger-to-preview p95 > 5 s | добавить 2 P-core и второй instance |
| Один background worker | растёт oldest pending job или ingest-to-searchable p95 | добавить второй PostgreSQL consumer |
| PostgreSQL jobs | PostgreSQL polling/locking подтверждённо ограничивает throughput | рассмотреть простой broker |
| Один центральный сервер | доступность одного узла не соответствует требуемому SLA | добавить standby/репликацию |
| CPU-only inference | CPU не выполняет SLA после настройки thread pools и масштабирования | исследовать GPU |

**Почему принято:** таблица задаёт измеримые границы. Агенты не должны предлагать следующий уровень сложности до выполнения соответствующего условия.

## 18. Основные технические риски сервера и display

### 18.2 Задержка загрузки коммерческих фотографий

Если фотографии загружаются в конце дня, промо-поиск не сможет найти их при выходе клиента. Необходимо согласовать workflow фотографа и измерять ingest-to-searchable.

### 18.3 Качество камеры

Плохой свет, motion blur, pose и несколько людей могут влиять сильнее, чем выбор между SFace и Buffalo M. Камера, освещение и зона захвата должны тестироваться вместе с моделями.


### 18.6 Один центральный сервер

Отказ сервера влияет на все SPA. Обязательны backup, мониторинг диска, автоматический restart процессов и документированный recovery procedure.

### 18.7 Локальная графическая сессия

Обновление Plasma, Chromium или видеодрайвера может нарушить показ на локальном HDMI-мониторе, но не должно останавливать Docker-сервисы. Display-сеанс должен проверяться после системных обновлений.

## 19. Финальная архитектурная формула сервера и display

~~~text
один центральный сервер для 10–15 SPA
+
Kubuntu 26.04 LTS и один системный пользователь
+
независимый автозапуск Docker Engine
+
Chromium display с рекламой, preview и QR
+
PostgreSQL + pgvector exact search
+
MinIO/S3-compatible storage
+
2 зарезервированных физических P-core
+
никаких Redis/Celery/priority/pause/ANN/clustering/margin
+
p50/p95/p99 как основание для любого будущего усложнения
~~~

Главный принцип:

> Сначала простая измеримая система. Новая инфраструктурная сложность добавляется только после того, как текущий bottleneck подтверждён реальными метриками.
